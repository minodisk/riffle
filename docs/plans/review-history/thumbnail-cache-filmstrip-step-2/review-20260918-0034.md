### Findings

1. **crates/core/src/arw.rs:80-85**: `read_ifd` silently returns `0` for the next-IFD link when `next + 4 > buf.len()`, i.e. exactly the truncated-prefix case. This is the one place in the parser where running off the end of the buffer produces a plausible-looking answer instead of an error: the IFD chain is cut short, `full` comes back `None` or as the largest JPEG among the IFDs that happened to fit, and `read_preview`'s fallback never fires because `parse` returned `Ok`. That contradicts the invariant the rest of the step is built on ("a truncated prefix must not produce a wrong answer"). Distinguish the two cases: `next + 4 > buf.len()` should `bail!` (the pointer is truncated), while a link value of `0` remains the normal end of the chain. The window is narrow (the 4 bytes after the last entry), but it is the only silent path left, and it is cheap to close.

2. **crates/core/src/arw.rs:180 / crates/core/src/reader.rs:47**: `parse` now follows the ExifIFD unconditionally, so an out-of-range 0x8769 / MakerNote / value offset turns a file that previously produced a preview into a hard error. For a truncated prefix that is correct (the fallback re-reads). For a genuinely corrupt EXIF pointer in a complete file it is a behaviour change for `preview`: the whole-file re-read fails the same way, and `map_err(|_| e)` then reports the *prefix* error, so the user gets e.g. `ASCII value out of range` where the old code showed the preview. Two things worth deciding here: (a) on the unbounded re-read, an out-of-range metadata offset could degrade to `None` rather than kill the preview (the truncation explanation no longer applies once the whole file is in memory); (b) at minimum, surface the whole-file error rather than the prefix error, since the former describes what is actually wrong with the file.

3. **crates/core/src/arw.rs:155-165**: the `SONY` header skip adds 12 to `at` after bounds-checking only `at + count <= buf.len()`. A MakerNote with `count` in 5..11 that starts with `SONY` lands `at + 12` past the MakerNote's own end; `read_ifd` then validates against `buf.len()`, not against `end`, so it happily parses whatever follows the MakerNote as an IFD. Only reachable on a malformed file and it cannot read out of bounds, but since the header is 12 bytes plus an IFD, requiring `count >= 12 + 2` before taking the skip (or clamping `read_ifd` to `end`) makes the intent explicit at no cost.

4. **README.md:55**: "the whole-file numbers match the ones Phase 2 recorded (7.3ms / 19.3ms mean)" overstates the agreement — 16.0 vs 19.3 ms is a 17% gap on the cold-read row, and the p95 moved 26.6 -> 30.0. The re-measurement is the right call and the caveats (IPC hop and `createImageBitmap` excluded, `purge` needs root so "first read" is not guaranteed cold) are accurately stated and match `learnings.md`. Soften "match" to something like "are in the same range as", so the table does not imply a tighter reproduction than the run-to-run noise supports.
