## Round 1

**Reviewed commit**: `3fa175beb794308e02b15e0ec24d73dd51de45bb` feat(app): add Move to Trash to the filmstrip's right-click menu

STATUS: NEEDS_FIX

### Findings

1. **crates/app/ui/src/main.ts:991-995 (`runTrash`, `paths` branch) / 949-975 (`trashFilesIn`)**: the strip's confirm closes `#trash-dialog` and ends `trashFlow` *before* `trash_files` is invoked, so for the whole run (seconds for a few hundred RAWs) the strip has the keyboard again, nothing on screen says a move is under way, and `trashFlow` is idle. The reject flow deliberately keeps the dialog open in the `running` phase with both buttons disabled until the invoke settles (`trashFlow.isOpen` routes every key to `trashKeydown`), and this path drops that guard. Concretely: a judgment key on a file being moved queues a sidecar write after the backend drained the writer (the moved RAW's `.xmp` / `.dop` can be re-created next to a missing RAW, or the write fails into `errors`), and a second `Move to Trash…` on the same still-listed files can be confirmed and invoked while the first is in flight, its files then failing per file. Fix: when no scan runs, keep the reject path's behavior — `trashFlow.run()` already moved the phase to `running`, so disable both buttons, invoke, and call `closeTrashDialog()` in both `.then` and `.catch` as the reject branch does. Only when the idle gate actually holds the move (scan running) close the dialog right away and let the held closure invoke (e.g. use `whenIdle`'s returned `held` flag, or check `scanRunning` before choosing). Also update `runTrash`'s header comment ("The run collects again under the backend's `Scans` lock …"), which now describes only the reject branch.
