## Round 1

**Reviewed commit**: `49f9cac4ee4ced8719aa4938e4d875f18e28095a` feat(core): read Nikon NEF files through the reader and the listing

STATUS: NEEDS_FIX

### Findings

1. **[crates/core/src/nef.rs:26-30]**: The whole-file retry depends on `parse` failing when the prefix is too short, but only IFD0 and the SubIFDs are checked. The Exif IFD is read through the lenient `exif::read`, which quietly turns an Exif IFD offset past `buf` into an empty entry list (`tiff.ifd_entries(at).ok()...unwrap_or_default()`). So a NEF whose Exif IFD starts past the 1 MiB prefix, or is cut off by it, parses `Ok` from `read_metadata` / `read_preview` with `capture_time`, `subsec`, exposure and so on all `None`. No retry happens, and `run_scan` stores that result in the index under the current `EXTRACTOR_VERSION`, so the capture-time sort and the meta pane stay wrong until the version is bumped. `arw.rs` treats this case as an error (`read_ifd(buf, at)?` in `exif`). The samples keep the Exif IFD within about 300 KB, but that fact belongs in the rationale, not in the correctness argument. The module doc also says "a structure that points past `buf` is an error", and the Exif IFD is such a structure. Suggested fix: in `parse`, find IFD0's 0x8769 entry. If it is present, require `tiff.ifd_entries(exif_at)?` and its next-IFD link (`tiff.u32(exif_at + 2 + 12 * n)?`), just as the SubIFD loop does, then leave the field values lenient. Add a case to `a_structure_past_the_buffer_is_an_error` with an Exif IFD pointer past the end.
2. **[crates/app/src/rename.rs:161]**: The PR makes `is_raw_file` accept `.nef`, so `rename_folder` and the file rename now accept `.NEF` names. But the rejection message still says `not a RAW file name (.ARW or .DNG)`, and the CLI's `no RAW (ARW/DNG) files in {dir:?}` (`crates/cli/src/main.rs:316`, `:386`) and the `list_arw_in` doc comment (`crates/app/src/commands.rs:155`, "List the RAW (ARW and DNG) files") are also out of date now. None of these are covered by Step 4's done-when, which names only `NO_FILES_TEXT` and the bench error, or by the plan's "the only user-facing strings are ..." survey. So they would outlive the whole plan. Either update them in this PR (generic wording such as "a RAW file name" avoids editing them again for CR3), or add them explicitly to Step 4's done-when and correct the plan's survey sentence.
