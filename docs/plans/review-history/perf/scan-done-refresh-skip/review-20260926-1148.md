## Round 1

**Reviewed commit**: `2e7135116da86615a6b14b6da1c881c0fe88299a` perf(app): skip the scan-done refresh when neither the reconcile nor the scan changed a row

STATUS: NEEDS_FIX

### Findings

1. **crates/app/src/commands.rs, crates/app/src/index.rs, crates/app/src/sidecar.rs (whole files)**: The commit converts all three files from LF to CRLF. `origin/main` has no `\r` in them, and HEAD has one on every line (3754 / 3569 / 2187). As a result `git diff --numstat` reports every line of all three files as rewritten (about 9.5k lines each way), even though the real change is 47/13, 108/24 and 2/2 lines (`--ignore-cr-at-eol`). That wipes out `git blame` for these files and will conflict with every other branch that touches them. Convert them back to LF (e.g. `dos2unix` on the three files, or `git add --renormalize .` after setting `core.autocrlf=false`, then re-commit) so the diff contains only the real change. Consider adding `* text=auto eol=lf` to `.gitattributes` to stop this happening again on Windows checkouts.
2. **crates/app/src/commands.rs:1108 (`scan_folder`, the joined previous scan)**: `changed` counts only the rows the two reconciles touch. It misses rows that a superseded scan of the same folder writes after the open-time `folder_entries` read. `openDirectory` calls `refreshEntries()` and then `startScan()`, and the two invokes run concurrently. `scan_folder` then sets the previous scan's cancel flag and awaits its handle, but a cancelled pass still commits its in-flight batch (see `canceling_after_the_first_batch_keeps_what_was_written` and `canceling_the_faces_pass_still_reports_what_was_written`). If that last batch lands after the open read's snapshot, the new scan's reconcile sees those rows as valid, so `todo` and `changed` are both 0. Before this change the `scan-done` read picked them up. Now `refreshOnScanDone` skips it, and because the scan-done read was what made it safe to skip at `faces-done`, `refreshOnFacesDone` skips as well. The strip then keeps the missing entries, or the missing eye sharpness if the previous scan was in its faces pass, until the next change. This happens when the same folder is reopened mid-scan (e.g. the `sidecar-format` reopen, or picking the folder again). Suggested fix: count a joined previous scan as a change (e.g. keep a flag when `previous` was `Some` and add 1 to `changed`). Switching folders during a scan would then cost one extra refresh. Also add a line to `refreshOnScanDone`'s doc comment about this assumption.
3. **docs/plans/20260926-scan-done-refresh-skip/plan.md:147**: Step 1 is ticked `[x]`, but `## Progress` still reads `(none yet)`. The plan's own `<pr-rules>` require the implementation PR to include the Progress entry along with the tick. Add a Step 1 entry (what shipped, and the CI clippy fix recorded in `learnings.md`).
