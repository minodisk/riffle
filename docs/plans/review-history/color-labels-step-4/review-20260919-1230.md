## Round 1

**Reviewed commit**: `5ec65b17d13c76a5a71825b848496b28f8d97d9b` feat(app): carry the colour label through the writer and set_rating

STATUS: NEEDS_FIX

### Findings

1. **[crates/app/ui/src/main.ts:551-557]**: This change can erase existing labels. `labels` is only filled for paths that are not in `touched`. `touched` is added to in `judge()` and is only removed from when the `set_rating` call fails. Suppose the user judges a file before its `folder_entries` row arrives. This happens on a first open while the scan is still indexing, or before the first `refreshEntries` resolves. In that case `judge()` sends `label: null`. Then `set_rating` stores no label and the writer strips the label that PhotoLab or Lightroom put in the sidecar. After that, every later refresh skips the label because the path is still in `touched`, so each further keypress sends null again. Before this step the writer never changed labels, so this data loss is new. The frontend never changes a label on its own in this step, so the `touched` guard does not need to cover `labels`. Update `labels` from every row whether or not the path is touched. Also make sure an unknown label cannot clear the sidecar. One way is to skip `label` in the invoke (or send a "keep" marker) when `entries` has no row for the path yet, and have `set_rating` keep the stored label in that case. Add a test for "judge before the row is known" that checks the label is kept.

## Round 2

### Findings

1. **[crates/app/src/commands.rs:913-920]** (partial repeat of Round 1 item 1): With `label_known: false`, the fallback is `Index::label`, which reads only the `ratings` row. The label from PhotoLab or Lightroom reaches `ratings` only after `store_sidecars` has parsed that folder's sidecars. If the user judges a file before that happens, for example on a first open while the scan or sidecar pass is still running, `Index::label` returns `None`. That is the same "no row yet" case the new test says the caller "must not treat as a real absence of label". Also add the test Round 1 asked for: a judgement made before any row or sidecar parse must keep the label that is already in the sidecar. The current test covers only the getter.

## Round 3

**Reviewed commit**: `d1ebaf565db151483d816dc93db1a0c416ce475a` fix: address local review round 2 findings

### Findings

1. **[crates/app/src/index.rs:484-497, crates/app/src/sidecar.rs:330-337]** (partial repeat of Round 2 item 1): The first write now keeps the label, but the label is still lost on the next keypress. When `label_known` is false and there is no row yet, `set_rating` inserts the row with `label` NULL. `mark_written` then clears `dirty` and records the new sidecar stat, but it never saves `resolved_label` into `ratings.label`. On the next open, `reconcile_sidecars` sees a matching stat and does not re-parse the sidecar, so `ratings.label` stays NULL for good. `folder_entries` then reports `label: null`, the frontend (with `entries.has(path)` true) sends `labelKnown: true, label: null`, and the writer strips "Red". The same thing happens within the session as soon as the next `refreshEntries` lands. Fix: in the `label_known == false` branch of `mark_written`, also `SET label = ?resolved` (still guarded on rating/pick). Extend the new sidecar test so it checks `ratings.label` / `entries("d")` equals `Some("Red")` after the flush, and then checks that a follow-up `label_known: true` judgement using that stored label keeps the label.
2. **[crates/app/src/commands.rs:648-652]**: Dirty rows are replayed on a folder open with `label_known: true` hard-coded. A row that `set_rating` created with `label_known: false` has `label` NULL and not "unknown". If the app crashes or quits before the writer drains, the next open replays it as "no label" and strips the sidecar's label. `store_sidecar_ratings` does not rescue this, because the stat has not changed and the row is not re-parsed. Persist the "label unknown" state in the row (for example, a nullable flag column, or leave `label` NULL together with a `label_known` column) and pass it through `dirty_rows` → `set_now`. Alternatively, have `set_rating` with `label_known == false` fill `label` from the current sidecar before inserting.

## Round 4

### Findings

1. **[crates/app/src/index.rs:510-515]**: The `label_known == false` branch of `mark_written` checks only `rating` and `pick` before it overwrites `label` and sets `label_known = 1`. It does not check whether the row still holds an unknown label. Here is a failing sequence. An unknown-label write resolves "Red" and is in flight. Meanwhile a newer judgement asserts a label (`label_known: true`, e.g. "Blue" once Step 6 adds the label keys) with the same rating/pick. The stale `mark_written` then overwrites `ratings.label` with "Red" and clears `dirty` on the newer row. After that, the newer write's own `mark_written` fails its `label IS 'Blue'` guard. The index shows "Red" while the sidecar has "Blue", and until the write lands the row is not dirty, so a crash in that window loses the judgement. Add `AND (label_known = 0 OR label IS ?6)` to the WHERE clause, so a row that has since asserted a different label is left dirty. Add a test next to `mark_written_only_clears_a_row_that_still_holds_the_written_value` that covers this.
