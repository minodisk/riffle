2. **[crates/app/src/rename.rs:100-107, crates/app/src/treewatch.rs:218-230]**: `treewatch::release_under` and `treewatch::restore` each take the `TreeWatch` lock and let go of it. Nothing stops `set_tree_watches` from running between the release and `std::fs::rename`, because `rename_folder` holds the `Scans` lock but not `TreeWatch`. Once Step 2 exists, any tree re-render that changes the drawn, expanded set during that window (for example a `tree-changed` re-list that arrives just then) sends a set that still contains the renamed folder and its descendants. `apply` then watches them again. On Windows the rename fails with `PermissionDenied`, and the user sees a rename error that has nothing to do with their input. The same window also lets a failed rename's `restore` add back a path the frontend dropped in the meantime. The frontend only resends when its set changes, so that stale watch would pin the folder until the next change. Suggested fix: hold the `TreeWatch` state lock for the whole release, rename and restore-on-failure sequence. One way is a `treewatch::with_released(app, &old, |..| std::fs::rename(..))` helper. Another is to return the `MutexGuard` together with the released list. Holding the lock is safe: the notify handler only takes the separate `keys` lock, never the `State` lock, so it cannot deadlock against a rename that holds `State`.
