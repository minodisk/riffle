### Findings

1. **crates/app/src/photolab.rs:344 (`a_lock_released_within_the_retries_yields_the_uuids`)**: The test passes even when the retry is removed. I set `BUSY_ATTEMPTS = 1` temporarily and ran `cargo test -p riffle-app photolab::tests::a_lock`, and both tests still passed (0.83 s). The cause is the timing. The release fires at `BUSY_TIMEOUT * 5 / 2` = 750 ms, but `learnings.md` measures one attempt at about 0.8 s of wall time on Windows, because `winLock` sleeps in addition to the busy handler's nominal 300 ms. So the lock is released while the first attempt is still in its busy handler, and that first attempt succeeds. The plan's "Done when" requires a delay "longer than one attempt and shorter than the total", and this test does not meet it, so nothing verifies the retry path. Fix: base the release delay on the measured per-attempt wall time rather than the nominal timeout. For example, release after about 2 s, which is past two attempts (about 1.6 s) and well under the six-attempt total of about 4.9 s. Alternatively, have `lookup` delegate to an internal function that returns the attempt count, and assert that the count is greater than 1. Then confirm the test fails with `BUSY_ATTEMPTS = 1`.
2. **docs/plans/20261005-photolab-busy-retry/plan.md:111-113**: Step 1 is checked, but `## Progress` still reads `- (none yet)`. The plan's own `<pr-rules>` require the implementation PR to include "the plan.md update (marking the step done + the Progress entry)". Add a Progress entry for Step 1.
