### Findings

1. **crates/app/src/sidecar.rs:198 (`raw_orientation`)**: A `files` row whose extraction failed stores `orientation = NULL` (see the `Err(message)` branch of `Index::write_batch`, index.rs:817). `IndexedFile.orientation` turns that NULL into `1` (`indexed_file`, index.rs:322). `Index::entry` still returns `Some(row)` for such a row, so `raw_orientation` yields `Some(1)` without trying `read_metadata`. An error row is common enough: `extract` fails the whole file when the preview does not decode (`thumbnail_jpeg` error or panic), even though IFD0 parsed fine and carries, say, `8`. Riffle then writes `Orientation = 1` into the `.dop`. Because "an existing `Orientation` is never touched", this value can never be corrected on a later write. That is the exact "foreign value rotates it wrongly" failure the plan sets out to avoid, and it contradicts the plan's "`None` when neither yields one". Fix: read the raw `Option<u16>` column. For example, add a one-statement `Index::orientation(path) -> Result<Option<Option<u16>>, String>` (the plan already suggests this), or `SELECT orientation FROM files WHERE path = ?1 AND error IS NULL`. Fall through to `read_metadata` when the row is missing or its column is NULL. Add a test with an error row (e.g. the existing `arw_with_preview(8, b"not a jpeg")` after a `run_scan`, which should produce such a row) that asserts `Orientation = 8,`.
2. **docs/plans/20260926-dop-orientation/plan.md:95**: Step 1 is marked `[x]`, but `## Progress` still reads `- (none yet)`. The plan's `<pr-rules>` require the implementation PR to include the Progress entry, and the previous plan had one (`- (2026-09-26) Step 1 complete`). Add the same entry.
