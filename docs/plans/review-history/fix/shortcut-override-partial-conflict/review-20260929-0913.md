### Findings

1. **crates/app/src/shortcuts.rs:303-320**: A partly applied override permanently loses a dropped key even when that key becomes free later in the same load, and the UI can produce this state. `learnings.md` says it cannot, but it can. Starting from the defaults, in the settings panel: add `w` to `previous`, remove `arrowleft` from `previous`, add `arrowleft` to `burstPrevious`, remove `arrowup` from `burstPrevious`, add `arrowup` to `previous`. Every step passes `check_bindable` / `remove`, and the stored value is `{"previous": ["w", "arrowup"], "burstPrevious": ["arrowleft"]}`. At load, the inner loop deadlocks: `arrowup` is still held by `burstPrevious`'s default, and `arrowleft` by `previous`'s default. The partial step then sets `previous = ["w"]` and drops `arrowup`. The rerun applies `burstPrevious = ["arrowleft"]`, which frees `arrowup`, but `previous` keeps `["w"]`. So the loaded keymap does not match what the user saved, `arrowup` is left unbound, and the next save of any shortcut writes `previous: ["w"]`, erasing `arrowup` from the store. Suggested fix: keep each partly applied override's requested keys, not only the `rest`. After the outer loop settles (or at the top of each outer iteration), recompute each partly applied action's keys as its requested keys filtered by `holder(i, key).is_none()`, in requested order. That only ever adds keys that are free at that point, so it cannot create a conflict. Add a regression test with the stored value above, asserting `previous == ["w", "arrowup"]`, `burstPrevious == ["arrowleft"]` and the `overrides()` round trip. Then correct the "remaining edge" bullet in `docs/plans/20260929-shortcut-override-partial-conflict/learnings.md` and the matching wording in the `docs/agents/tauri-app.md` entry, if the rule changes.
