## Round 1

**Reviewed commit**: `93098214a8dd98baba6cbdceab6a99d4181e76de` fix(app): resize oversized previews in the decode worker on Linux

STATUS: NEEDS_FIX

### Findings

1. **crates/app/ui/src/main.ts:1346-1349**: The stale branch after `previewPixelLimit.then(...)` calls `requestPreview()`, but `inFlight` was already cleared before the await. So a page turn during the await was never blocked: `show()` → `requestPreview()` already started its own request for the new `seq`. Calling `requestPreview()` again here can start a duplicate `preview` invoke for the same `seq`. Scenario: request A (seq 1) awaits the unresolved limit, the user turns to seq 2, request B's invoke returns and also awaits, and the limit resolves. A's callback runs first (FIFO), sees `inFlight === false`, and starts request C for seq 2. B and C then both post seq 2 to the worker. The first worker response runs `orientations.delete(2)` / `pageTimings.delete(2)`. If C's `orientations.set(2, …)` happened before that delete, C's response draws with the default orientation 1, so a portrait frame shows unrotated, and the decode runs twice. The window is only the startup race, but the fix is trivial: in this branch, `return` without calling `requestPreview()`. The re-request in the pre-await branch exists only because `inFlight` blocked the page turn there, and that does not apply after the await. Alternatively, keep `inFlight = true` until after the await. Also update the matching bullet in `docs/plans/20260924-linux-preview-pixel-limit/learnings.md`.
