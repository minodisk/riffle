## Round 1

**Reviewed commit**: `a04c02c089a6f070039be0b42024efede649df11` fix(app): clear the main preview when the current file's preview fails

STATUS: NEEDS_FIX

### Findings

1. **[crates/app/ui/src/main.ts:543 / crates/app/ui/style.css:980]**: `#empty` is `position: absolute; inset: 0` over `#viewer` and takes pointer events. Until now it only showed when there was no file to view, so blocking the canvas did not matter. The new `"preview-failed"` state shows it over a viewer that still has a current file, so it now swallows the canvas's `contextmenu` handler (main.ts:1206) and `click` handler (main.ts:1202). Right-clicking the main preview of the failed file (very likely the file the user wants to reject) no longer opens the app's context menu, and since nothing calls `preventDefault`, the webview's native menu probably opens instead. Fix: add `#empty[data-state="preview-failed"] { pointer-events: none; }` in `style.css` so events fall through to the canvas. The plan allows a `style.css` change when a rule is needed, and this one is.
2. **[crates/app/ui/src/main.ts:543]**: `renderEmpty()` shows `"preview-failed"` whenever `previewFailedSeq === seq`, even in Compare (`comparing`) or 1:1 (`zoomed`). Those modes draw from their own sources (`compareFrames` via `loadCompare`, `crop` via `requestCrop`), and the plan says they already handle their own failures. If the main `preview` request fails while Compare shows the other candidates, or while a 1:1 crop of the same file succeeds, "The preview of this file could not be shown." sits centered over images that did render, which is misleading. Fix: pass `previewFailedSeq === seq && !comparing && !zoomed` (or similar) to `emptyState`. Then make sure `renderEmpty()` runs when either mode toggles. `toggleZoom` / `stopComparing` callers already reach `renderMeta()` in most paths, but check that each one does.
