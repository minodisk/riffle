### Findings

1. **crates/app/ui/src/main.ts:127-148 / 252-271**: `refreshEntries` guards only on `folderToken`, which does not distinguish two refreshes issued under the *same* token for *different* folders. `openFolder` bumps `folderToken` first, but `openDir` (and `scanId`) are only updated later, inside the `list_arw` `.then`. In the window between the two, a `scan-progress` event of the **old** folder still matches the old `scanId` and fires `refreshEntries()` with `dir = old folder` but `token = the already-bumped, new folderToken`. If that response lands after the new folder's own refresh, `entries.clear()` + refill repopulates the map with the previous folder's rows, i.e. exactly the "map left holding the old folder's rows" case `folderToken` was meant to cover. The paths differ, so the visible effect is a missing box rather than a wrong one, and it self-heals on the next progress/`scan-done`, but the guard should be exact: capture `dir` (already done) and drop the response when `dir !== openDir || token !== folderToken`.

2. **crates/app/ui/src/main.ts:315-319**: the "only when the current file's row is missing" condition does not actually bound the re-read rate in the case it matters. When the user pages ahead of the scan — the scenario the whole guard exists for — `entries.has(files[index])` stays false for as long as the scan has not reached that file, so every `scan-progress` tick (~10/s) issues another full `folder_entries` read of the folder (all rows). That is the 5000-rows-ten-times-a-second cost the comment claims to avoid, just conditioned on a predicate that is true precisely then. Add an in-flight flag (also fixing the unordered-response clobber: two overlapping refreshes both `clear()` + refill, so an older snapshot can overwrite a newer one) and/or a minimum interval between refreshes. As written, the comment overstates the protection.

3. **crates/app/ui/src/main.ts:252-254 vs 127-137**: `openFolder` increments `folderToken` before `pick_folder` resolves, so cancelling the picker invalidates any `refreshEntries` still in flight for the folder that remains open; its rows are discarded and the box does not appear until the next `scan-progress`/`scan-done` (never, if the scan already finished). Bumping the token only once a folder has actually been chosen, or keying the guard on `openDir` as in item 1, avoids this.

4. **crates/app/ui/src/main.ts:91-125, 154-172**: the transform itself checks out for Orientation 1, 6 and 8 — the box is scaled in unrotated preview space and stroked inside the same `save`/`translate`/`scale(dpr)`/`rotate` block as `drawImage`, so it inherits the rotation, and `side = min(drawWidth, drawHeight) * 0.05` is rotation-invariant, giving the same physical size in portrait and landscape. Orientation 3 is the gap: `draw()` applies no rotation for it (`quarterTurn` and the `rotate` branches cover only 6 and 8), so a 180-degree file is displayed upside down and the box follows it — consistent with the image, hence not wrong relative to the pixels, but it will not sit on the subject as the plan's criterion states. This is pre-existing in `draw()` rather than introduced here; either handle `orientation === 3` with `context.rotate(Math.PI)` (one line, and the box then comes along for free) or record it explicitly as a deferred item in `learnings.md`, since the step's criterion is about where the box lands for the user.

5. **crates/app/ui/src/main.ts:165-171**: the two `strokeRect` calls share the same rect and are centred on it, so the 4px black under the 2px white leaves only a 1px black halo on each side. Over a white jersey that is a thin outline for a 2px line; widening the black to 6px (2px of halo per side) costs nothing and makes the box legible on both a blown-out highlight and a dark background. Also `context.lineJoin = "miter"` is the canvas default and nothing in the file changes it, so the assignment can go.
