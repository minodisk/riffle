## Round 1

**Reviewed commit**: `3918dc4fe278d2d40483e1e8b5cc5879bba9547f` feat(app): embed each RAW file in a third scan pass behind the aiEnabled setting

STATUS: NEEDS_FIX

### Findings

1. **[crates/app/src/ai.rs:112-133, 135-188, 219-265]**: Turning AI off and back on while a download is running can break the new download. `switch(false)` sets the old download's `cancel` and takes its entry, so a quick `switch(true)` sees `download.is_none()` and starts a second thread on the same `MODEL_FILE.part`. The old thread might still be in `fetch`, waiting up to 30 s for connect/headers, or blocked in `src.read`. If it then reaches `install`, its `File::create(&part)` truncates the new thread's file. Its next cancel check returns `Err`, and its cleanup runs `remove_file(&part)`. That deletes the `.part` the new thread is writing into. std opens files with `FILE_SHARE_DELETE` on Windows, so the delete succeeds there too. The new thread then downloads all 378 MB and fails at the final `rename` with a "The model download failed" error. Fix: give each download its own part file (e.g. `.part-{n}` from a counter, with cleanup of stale `.part*` files on start), or keep the canceled download's handle and do not spawn a new one until the old thread has exited (start the new download from the old thread's exit path if the setting is still on by then).
2. **[crates/app/src/commands.rs:1169-1177 / crates/app/src/index.rs:1255-1281]**: `stop_embedding`'s doc says it runs "before an operation that deletes or moves index rows (`clear_index`, the renames), so no batch lands after them". It does not do that. It only sets `cancel`. A worker's `flush` blocked on the index lock, and the task's trailing `flush(std::mem::take(&mut *lock(&pending)))` after `embed_all` returns, both write once `clear()` / `rename_dir` / `rename_file` release the lock. The `drop_stray_embeddings` fallback does not fully cover this. After `clear()`, a folder with dirty ratings keeps its `folders` row, so its late rows are not strays. The next `reconcile` keeps them too, because their stat still matches the listing. So "Clear Cache" can leave embeddings behind, and `clear()`'s summary and the `VACUUM` miss them. After `rename_file`, the late row for the old path stays under a live `dir` until that folder is reconciled again. Suggested fix: make `write_embeddings` insert only when a `files` row with the same `path`, `size` and `mtime_ns` exists, e.g. `INSERT ... SELECT ?1, ?2, ... FROM files WHERE path = ?1 AND size = ?3 AND mtime_ns = ?4 ON CONFLICT ...`. Every late write after a clear, rename or reconcile would then be a no-op, and `drop_stray_embeddings` could likely go. At minimum, correct the `stop_embedding` doc so it no longer promises that no batch lands afterward.

### Dismissed

- Item 2 (partly): the `stop_embedding` doc is corrected so it no longer
  promises that no batch lands afterwards. The guarded
  `INSERT ... SELECT ... FROM files` in `write_embeddings` is not done in this
  step because it needs a rework of the embedding tests (they write
  embeddings without `files` rows); it is recorded in `learnings.md` under
  `## Deferred issues (todo candidates)`.
- Item 1 is fixed: each `install` call writes its own `.part-{n}` file, and
  `AppAi::new` removes stale part files at startup.
