### Findings

1. **[crates/app/src/commands.rs:1253-1296]**: Both the pre-dialog refusal and the under-lock re-check only test `state.running.is_some()`, but a scan is invisible in `running` for the whole of its prepare phase. `scan_folder` (line 720-726) mints the id, *takes* `running` out of the state and then spends the listing, `reconcile` and `reconcile_sidecars_of` phases with no lock held and `running == None`; `pending` is only populated at the very end (line 845). So a `clear_index` issued while a folder is opening passes both checks, `Index::clear` runs against its documented precondition ("call this with no scan running"), and the subsequent `start_scan` then scans a `todo` computed against rows the clear has just deleted — re-creating the folder row and thumbnails that were supposed to be gone, i.e. exactly the clobbering the re-check was meant to prevent. `spawn_eviction` has the same hole, but it only fires once at startup, whereas this is user-triggered at an arbitrary moment. Suggested fix: make the prepare phase visible in `ScansState` (e.g. a `preparing` counter/flag set under the lock where the id is minted and cleared under the lock in `start_scan` and on every early return of `scan_folder`) and refuse in `clear_index` when it is set or when `pending` is non-empty, rather than on `running` alone.

2. **[crates/app/src/commands.rs:1344-1351]**: `the_size_base_follows_the_platforms_file_manager` re-states the `cfg!` of the definition it checks, so it cannot fail for any change to `SIZE_BASE` that keeps the same `cfg!` shape and it adds no coverage beyond the compiler. Either drop it or turn it into something with content (e.g. assert that `format_bytes(1_000_000_000, SIZE_BASE)` renders as the platform's file manager would).
