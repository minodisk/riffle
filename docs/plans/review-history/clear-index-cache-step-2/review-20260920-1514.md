## Round 1

**Reviewed commit**: `fe8fb8ed6b253916a998dfbb9e94c8c67df8332c` feat(app): add the index_size and clear_index commands

STATUS: NEEDS_FIX

### Findings

1. **[crates/app/src/commands.rs:1253-1296]**: Both the pre-dialog refusal and the under-lock re-check only test `state.running.is_some()`, but a scan is invisible in `running` for the whole of its prepare phase. `scan_folder` (line 720-726) mints the id, *takes* `running` out of the state and then spends the listing, `reconcile` and `reconcile_sidecars_of` phases with no lock held and `running == None`; `pending` is only populated at the very end (line 845). So a `clear_index` issued while a folder is opening passes both checks, `Index::clear` runs against its documented precondition ("call this with no scan running"), and the subsequent `start_scan` then scans a `todo` computed against rows the clear has just deleted — re-creating the folder row and thumbnails that were supposed to be gone, i.e. exactly the clobbering the re-check was meant to prevent. `spawn_eviction` has the same hole, but it only fires once at startup, whereas this is user-triggered at an arbitrary moment. Suggested fix: make the prepare phase visible in `ScansState` (e.g. a `preparing` counter/flag set under the lock where the id is minted and cleared under the lock in `start_scan` and on every early return of `scan_folder`) and refuse in `clear_index` when it is set or when `pending` is non-empty, rather than on `running` alone.

2. **[crates/app/src/commands.rs:1344-1351]**: `the_size_base_follows_the_platforms_file_manager` re-states the `cfg!` of the definition it checks, so it cannot fail for any change to `SIZE_BASE` that keeps the same `cfg!` shape and it adds no coverage beyond the compiler. Either drop it or turn it into something with content (e.g. assert that `format_bytes(1_000_000_000, SIZE_BASE)` renders as the platform's file manager would).

## Round 2

**Reviewed commit**: `b23363f54c9e7ae0454307edd347fdd8a74ab1eb` fix: address local review round 1 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 2 / dismissal accepted 0 / re-raised 1

### Findings

1. **[crates/app/src/commands.rs:756-763]** (narrowed repeat of Round 1 item 1): `Preparing::new` takes the `Scans` lock a *second* time, after the block that mints the id and does `state.running.take()` has already released it. In that window `running` is `None`, `preparing` is still 0 and `pending` is empty, while the previous scan's blocking task is still alive and writing rows (it is only cancelled and joined further down, after `Preparing::new`). A `clear_index` that acquires the lock exactly there passes the under-lock re-check and runs `Index::clear` — `VACUUM` and the WAL truncate included — concurrently with a live scan, i.e. the precondition the flag was added to enforce. Fix: increment inside the same guard that takes `running` (e.g. `state.preparing += 1;` in that block and have `Preparing` only own the decrement, or a `Preparing::start(&mut state, app.clone())` constructor taking the existing guard), so the prepare phase is never invisible.

2. **[crates/app/src/commands.rs:1233-1248]**: `format_bytes` can print a figure equal to the base because each step compares the *already divided* value against `base` before dividing again: `format_bytes(999_999_999, 1000)` gives `"1000.0 MB"` and `format_bytes(1_073_741_823, 1024)` gives `"1024.0 MB"`, instead of stepping up to GB. Compare against `base` *after* rounding to one decimal (or step up when the ratio is `>= base - 0.05 * base_step`), and add a test for the just-below-a-power value.
