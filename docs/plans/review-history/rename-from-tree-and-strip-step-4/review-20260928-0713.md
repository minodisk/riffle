## Round 1

**Reviewed commit**: `c270cf662146ea9c7efc65d1fd0ec758003da601` feat(app): rename a file inline from the strip

STATUS: NEEDS_FIX

### Findings

1. **[crates/app/ui/src/main.ts:2181 (`resync(newPath)` in `renameFile`)]**: The rescan always anchors on the renamed file, even when the user has moved on by the time `rename_file` resolves. The planned "a click away confirms" path hits this every time. The user clicks cell B while editing A, the input's `blur` confirms, the click then focuses and `show()`s B, and then the invoke resolves and `resync(newPath)` runs `refilter(newA, true)`. That sets `index` to A's new index, and `mustReshow(false, newA, newA)` is false, so `show()` is skipped. The viewer and the meta rows stay on B while `files[index]` (the strip highlight and the target of every judgment key) is A. A rating key pressed next rates A while B is on screen. Pressing Enter and then paging with an arrow before the invoke returns does the same. This is the unconditional re-anchor that `docs/agents/tauri-app.md` "Undo must re-anchor conditionally" warns about. Fix: anchor on the new path only when the renamed file is still the focused one, e.g. `resync(files[index] === path ? newPath : undefined)` (read before the maps are touched). The default `files[index]` then keeps B.

2. **[crates/app/ui/src/main.ts:2150-2183 (`renameFile`) / main.ts:473]**: When the renamed file is the shown one (the normal case), the meta pane keeps showing the old file name. `renderMeta` prints `meta.name` whenever `meta` is loaded and not stale. `meta` was fetched for the old path, and the anchored rescan skips `show()` because `files[index] === anchor`, so nothing refreshes it. The strip cell and the title bar show the new name, but the meta pane's name row shows the old one until the user pages away and back. Fix: in the success branch, when the renamed file is the focused one, update the loaded metadata's name (e.g. `if (meta !== null && files[index] === path) meta = { ...meta, name: baseName(newPath) }`, set before `resync`, whose `refilter` calls `renderMeta`), or force a re-show.

3. **[crates/app/ui/src/main.ts:2169-2172]**: Only undo / redo batches that reference nothing but the old path are dropped. A mixed batch (a multi-selection judgment, reject-rest) keeps a `Judgment` whose `path` is the old, now nonexistent path, so undoing it later `set_rating`s that path and mints the orphan sidecar the comment says this avoids. `trashRejected` has no better option because its file is gone, but here the file still exists under `newPath`. Rewriting `entry.path` from `path` to `newPath` in both stacks keeps undo working for the renamed file and removes the orphan case entirely. A small `History` method that maps entries, or mutating the `Judgment` objects in place, would do it. If you keep the drop-only behavior, at least drop the old path's entries from mixed batches too.

## Round 2

**Reviewed commit**: `afb581d5fabbaadf60dc7b867e8f482e28bae6f8` fix: address local review round 1 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 3 / dismissal accepted 0 / re-raised 0

### Findings

1. **[crates/app/ui/src/main.ts:2191 (`resync(focused ? newPath : undefined)`) / main.ts:2345-2358 (`resyncAnchor`)]**: The Round 1 item 1 fix only holds when the rescan runs right away. The `scanRunning` gate applies when an edit starts (context menu, `canRename`), but it is not checked again at confirm. The edit also deliberately survives a switch to another app (the `document.hasFocus()` blur guard), and coming back fires `tauri://focus` → `resync()`, which starts a scan. So Enter pressed after an app switch reaches `renameFile` while `scanRunning` is true. `resync(newPath)` then only stores `resyncAnchor` and defers until `faces-done`. Until then, (a) `files` / the strip still hold the old, now nonexistent path while `ratings` / `flags` / `labels` / history have already moved to `newPath`. A judgment key on the focused cell rates `files[index]` (the old path), which sets `set_rating` on a gone file (an orphan sidecar, or an error) and splits the marks across two keys. And (b) the stored anchor is applied unconditionally when the deferred rescan finally runs. If the user paged to B in the meantime, `refilter(newA)` moves `index` to A, while `mustReshow(false, newA, newA)` skips `show()`, so B stays on screen with A as the judgment target (the same symptom as Round 1 item 1). Fix: either refuse the confirm while a scan runs (re-check `scanRunning` in `renameFile` / `finishRename`, set the "a scan is running" status, and skip the invoke), or make the rename's effect on `files` immediate and its anchor conditional. For the second option, swap `path` → `newPath` in `allFiles` / `files` / `fileIndex` in place at resolve time, and have the deferred rescan anchor on the new path only when `files[index]` is still that file (e.g. store `{ from, to }` and resolve it when the rescan actually runs, rather than a bare `resyncAnchor`).

### Findings

1. **[crates/app/ui/src/main.ts:2188-2204 (in-place patch of `files` in `renameFile`) / main.ts:1084 (`filterListChanged` early return in `refilter`)]**: The in-place patch fixes the Round 2 race, but it now leaves the strip cell, the meta pane and the title bar showing the old name. `renameFile` writes `newPath` into `files` before `resync()` runs. When the rescan's `list_arw` lands, `ordered().filter(passes)` returns the same list `files` already holds whenever the rename does not change the file's position. That covers the default capture-time sort, and a name sort where the new name sorts to the same place. So `filterListChanged(files, next, false)` is false and `refilter` returns early. `strip.setFiles` never runs, so the visible cell's `name` span, which `createCell` filled from the old path, keeps the old name, and the strip's `indexOf` still maps the old path (a later `markReady(newPath)` is ignored). `renderMeta` never runs either, so the `meta.name` patch (the Round 1 item 2 fix) never reaches the screen, and `renderTitle` keeps the old name in the title bar. The same holds while a deferred rescan waits for `faces-done`. (`files` is the very array the strip holds, since `refilter` passes it to `strip.setFiles` by reference, so the mutation also bypasses the strip's own bookkeeping.) Fix: after the in-place patch, refresh the display explicitly. For example, add a `strip.renamePath(at, newPath)` that updates the strip's `indexOf` and the cell's `name.textContent` (if the cell is live), then call `renderMeta()` (which also calls `renderTitle`). Alternatively, rebuild the strip by calling `strip.setFiles(files, true)` plus the `setRating` / `applySharpness` / `applyBursts` / `applyCandidates` / `paintSelection` / `setCurrent` / `renderMeta` sequence that `refilter` runs after its early-return check. Either way, add a test or a manual check that a capture-time-sorted rename shows the new name in the cell and the meta pane without paging away.
