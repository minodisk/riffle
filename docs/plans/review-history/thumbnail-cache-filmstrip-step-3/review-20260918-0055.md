# Review: thumbnail-cache-filmstrip-step-3

## Round 1

**Reviewed commit**: `1f27b2846b3f81c82db5f79d13f88167f0558a98` feat(core): extract a folder's metadata and thumbnails in parallel

STATUS: NEEDS_FIX

### Findings

1. **crates/core/src/scan.rs:63 / crates/cli/src/main.rs:165**: `threads == 0` is
   accepted silently and then panics. `ThreadPoolBuilder::num_threads(0)` does not
   error — it means "use the default", so `extract_all(paths, 0, ..)` quietly runs
   on a default-sized pool instead of the size the caller asked for, which
   contradicts the module doc ("the caller sizes it"). In the CLI it is worse:
   `riffle-cli scan <dir> 0` builds `last = vec![start; 0]` and the first
   `last[w]` in `on_item` panics with an index-out-of-bounds, which then unwinds
   through rayon and out of `extract_all`. Step 4 computes its thread count
   (`cores - 2`) at runtime, so a 0 or 1-core machine can hit the same path.
   Suggested fix: clamp or reject in `extract_all` (`if threads == 0 { return
   Err(..) }`, or `.num_threads(threads.max(1))`) so the pool size is always the
   one the caller named, and validate the CLI argument the same way.

2. **README.md:66-92 / docs/plans/.../learnings.md:96-121**: the (b) table is
   labeled "first read" / "the disk-bound number", but the measurement cannot
   support that label, and it is the sole basis of the bolded "**the 30-second
   target holds on the internal SSD**". The scan only reads the ~1 MiB prefix of
   each file (`reader::HEAD_LIMIT`), and that prefix is exactly the data `cp` had
   just written — ~100 MB of heads for a 4.5 GB copy, almost certainly still in
   the page cache on a 12-core Mac. So (b) is closer to a warm-head number with
   some write-back cost than to a cold read, and the write-order caveat compounds
   it rather than explaining it away. The caveat paragraph is honest about
   `purge` needing root and about only the user being able to measure a real
   folder, but the headline claim is stated more strongly than the data allows.
   Suggested fix: relabel (b) as "freshly written copies, page cache not
   guaranteed cold" rather than "first read"/"disk-bound", and soften the
   conclusion to something the data supports, e.g. "the CPU cost leaves ~25s of
   headroom against the 30s target; whether it holds depends on the disk, which
   these numbers do not establish". The single-threaded 34.9s and the ~4.5s CPU
   floor are solid and can stay as stated.

3. **crates/core/src/scan.rs:53-76**: the `extract_all` doc promises delivery
   semantics but says nothing about a panic *inside* `on_item`. Today such a
   panic unwinds out of `par_iter::for_each`, cancels the remaining items, and
   propagates out of `extract_all` as a panic (not an `Err`), leaving an
   arbitrary subset of indices delivered. That is a defensible contract, but Step
   4 will call this from a Tauri command with shared SQLite/state behind a mutex,
   where an unwind mid-callback poisons that mutex and leaves the index
   half-written. Suggested fix: state the contract in the doc comment — "`on_item`
   must not panic; a panic in it aborts the scan and propagates" — so Step 4
   knows to keep the callback panic-free (or wrap it itself).
