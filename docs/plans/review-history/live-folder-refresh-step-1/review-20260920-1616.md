## Round 1

**Reviewed commit**: `fcdb0c3768754717e4ccc140ed7a2b76c2c6432f` feat(app): rescan the open folder on focus and File > Reload Folder

STATUS: NEEDS_FIX

### Findings

1. **crates/app/ui/src/main.ts:1041**: `scanRunning = true` assumes a `scan-done` always follows `start_scan`, but the backend has paths where it never fires: `start_scan` (crates/app/src/commands.rs:906-918) returns `Ok(())` without spawning the scan when `state.latest_id != scan_id`, when the pending entry is gone, or when `AppIndex` is `None` — and in the `AppIndex::None` case `scan_folder` itself (commands.rs:775-781) returns a fresh `scan_id` without ever registering a pending scan, so that path is reached on every open. `scanRunning` then stays `true` for the rest of the folder's life and every later `resync()` (focus and `Reload Folder`) silently turns into a `resyncPending` that is never drained. Suggest making the flag self-clearing rather than event-dependent: e.g. clear `scanRunning` (and `drainResync()`) when `start_scan` resolves and no `scan-done` for that `scanId` has arrived, or have the backend always emit `scan-done` for a `scan_id` it handed out.

2. **crates/app/ui/src/main.ts:1047, 1037-1039**: `startScan`'s `catch` and its stale-token early return both leave `resyncPending` set without calling `drainResync()`, so a rescan requested during a scan that then fails is dropped (it is only picked up by the *next* unrelated `scan-done`). `resync` is careful to `drainResync()` on both of its own exits; `startScan` should do the same — add `drainResync()` to the `catch` and to the `token !== folderToken` return. (The `learnings.md` "Deferred issues" entry judges this harmless, but the failure path — not just the stale-token one — means a user-visible `Reload Folder` press can be swallowed with no retry, which is cheap to fix with the one call the sibling function already makes.)

## Round 2

**Reviewed commit**: `3847e1cb4bd3cc0a59d9c30f763ebcafa11119b3` fix: address local review round 1 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 2 / dismissal accepted 0 / re-raised 0

### Findings

1. **crates/app/ui/src/main.ts:1041 (`startScan`)**: `scanRunning = true` is set only *after* `scan_folder` resolves, so the whole prepare phase (the folder listing plus the index and sidecar reconcile — the expensive part for a large folder) runs with `scanRunning === false`. A `resync()` triggered in that window is not deferred; it starts a second `scan_folder`, which mints a new `latest_id` and strands the first one. The window is easy to hit: dismissing the Open Folder dialog gives the main window focus, firing `tauri://focus` while `openDirectory`'s own `startScan` is still preparing. If the second `scan_folder` resolves first, the first one's late `.then` overwrites `scanId` with the superseded id, so the real scan's `scan-done` no longer matches and `scanning`, `strip.refresh()` and `refreshEntries()` are never run for it (the folder's freshly indexed rows and thumbnails stay unshown until some other trigger). Suggest setting `scanRunning = true` at the top of `startScan`, before invoking `scan_folder`, and clearing it on both the stale-token early return (alongside the `drainResync()` already there) and the `catch`; that makes the deferral cover the prepare phase and keeps two `scan_folder` calls from overlapping.

## Round 3

### Findings

1. **crates/app/ui/src/main.ts:1035-1039, 1051-1053 (`startScan`)**: both exits that clear the shared state (`scanRunning = false; drainResync()`) run unconditionally, including when the call belongs to a folder that is no longer open. In the stale-token branch the token check has just proven the call is stale, yet it still writes the *current* folder's `scanRunning` flag. Sequence: folder A's `startScan` is awaiting `scan_folder`; the user opens folder B, so `openDirectory` sets `scanRunning = false` / `resyncPending = false` and its own `startScan` sets `scanRunning = true`; A's late `.then` then clears `scanRunning` for B's in-flight scan and calls `drainResync()`. The `catch` has the same hole (an error raised after a folder switch). Suggest guarding both: only `scanRunning = false; drainResync()` when `token === folderToken`, and in the stale branch simply `return` otherwise.

### Findings

1. **crates/app/ui/src/main.ts:1036, 1058 (`startScan`'s ownership check)**: switching the check from the token to `folder !== openDir` fixes the cancelled-dialog case, but it no longer detects a **re-open of the same folder**, which the code does on purpose: the `sidecar-format` and `index-cleared` listeners call `openDirectory(openDir, newFolderToken())` (lines ~1295 and ~1307), and the picker/drop can also land on the currently open path. Sequence: folder A's `startScan` is awaiting `scan_folder`; `index-cleared` fires, `openDirectory(A, ...)` resets `scanRunning = false` / `resyncPending = false` and its own `startScan(A)` sets `scanRunning = true` and is in flight; A's *old* `.then` then sees `folder === openDir`, so it proceeds, overwrites `scanId` with the superseded id and invokes `start_scan` for it. The backend now answers that superseded id with `emit_empty_scan_done`, and because `scanId` points at it the frontend's `scan-done` listener runs: `scanRunning = false`, `strip.refresh()` / `refreshEntries()` on a just-cleared index, and `drainResync()` — so a focus-triggered `resyncPending` drains while the real scan is still running, giving the second `scan_folder` stampede Round 2/3 closed. Suggest an ownership check that is per-call rather than per-folder: mint a monotonic `scanSeq` at the top of `startScan`, keep it in a module-level `currentScan`, and have both the `.then` and the `catch` return early unless their captured seq is still `currentScan` (this also subsumes the `openDir` comparison).
