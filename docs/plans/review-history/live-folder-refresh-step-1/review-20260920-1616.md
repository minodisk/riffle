### Findings

1. **crates/app/ui/src/main.ts:1041**: `scanRunning = true` assumes a `scan-done` always follows `start_scan`, but the backend has paths where it never fires: `start_scan` (crates/app/src/commands.rs:906-918) returns `Ok(())` without spawning the scan when `state.latest_id != scan_id`, when the pending entry is gone, or when `AppIndex` is `None` — and in the `AppIndex::None` case `scan_folder` itself (commands.rs:775-781) returns a fresh `scan_id` without ever registering a pending scan, so that path is reached on every open. `scanRunning` then stays `true` for the rest of the folder's life and every later `resync()` (focus and `Reload Folder`) silently turns into a `resyncPending` that is never drained. Suggest making the flag self-clearing rather than event-dependent: e.g. clear `scanRunning` (and `drainResync()`) when `start_scan` resolves and no `scan-done` for that `scanId` has arrived, or have the backend always emit `scan-done` for a `scan_id` it handed out.

2. **crates/app/ui/src/main.ts:1047, 1037-1039**: `startScan`'s `catch` and its stale-token early return both leave `resyncPending` set without calling `drainResync()`, so a rescan requested during a scan that then fails is dropped (it is only picked up by the *next* unrelated `scan-done`). `resync` is careful to `drainResync()` on both of its own exits; `startScan` should do the same — add `drainResync()` to the `catch` and to the `token !== folderToken` return. (The `learnings.md` "Deferred issues" entry judges this harmless, but the failure path — not just the stale-token one — means a user-visible `Reload Folder` press can be swallowed with no retry, which is cheap to fix with the one call the sibling function already makes.)
