## Round 1

**Reviewed commit**: `2f9a6afed047e7e9dfcf3f4fcbee181cd0463cee` feat(app): switch the sidecar format from a native Sidecar menu

STATUS: NEEDS_FIX

### Findings

1. **crates/app/src/commands.rs:323-334**: `switch_sidecar_format` drains the writer *before* it updates `AppSidecarFormat`, so a rating set while the drain runs (the UI is still live, and the drain can take up to `DRAIN_TIMEOUT`) is queued with the old format (`commands.rs:634` reads the format when the rating is set) and misses the drain. `reset_sidecars` then clears that dirty row's stat, and later the writer writes the row to the *old* format's sidecar and `mark_written` marks it clean with the old file's stat. The judgment never reaches the new format's sidecar, and the next reconcile compares a new-format listing against an old-format stat. Fix: set `AppSidecarFormat` to the new format first, then flush (which still drains the old-format entries already queued), then persist and `reset_sidecars`. Any rating made after the swap is queued in the new format and stays dirty through the reset, so it is written correctly. Add a test that sets a rating between the swap and the reset.
2. **crates/app/src/main.rs:106-121**: The `format == current` check reads the state before the `spawn_blocking` task sets it, so two quick clicks (XMP→DOP→XMP) can start two switches that run concurrently. Their drain, save, state write and reset can then interleave, which may leave the persisted setting, the in-memory state and the menu check disagreeing. Fix: serialize switches, for example by holding a dedicated `Mutex<()>` for the whole of `switch_sidecar_format` and re-checking the current format inside it (skip the switch if it already matches).

### Dismissed

1. (partial) The reordering fix itself was applied (`AppSidecarFormat` is now set before the drain, and persisting/`reset_sidecars` happen after). The "add a test that sets a rating between the swap and the reset" part is dismissed: `switch_sidecar_format` takes a real `tauri::AppHandle` and reads `tauri_plugin_store`-backed settings, and this codebase has no `tauri::test` mock-app harness anywhere (all the existing unit tests in `commands.rs` exercise the plain functions like `reconcile_sidecars_of` directly, never an `AppHandle`-taking command). Building that harness from scratch (mock runtime, store plugin wiring) is disproportionate to this one-line reordering fix, whose correctness is straightforward to verify by inspection. Deferred to `learnings.md` as a follow-up.
