### Findings

1. **crates/app/ui/src/main.ts:670-676 (runTrash) with main.ts:1452-1461 (step)**: `undoTrash` puts the restored RAWs into `allFiles` right away so that an undo pressed before the rescan lands still reaches their judgments. That window is intended by the plan, but in it the redo state comes out wrong. `runTrash` has already deleted `ratings` / `flags` / `labels` for every moved path. Nothing refills them until the rescan's `folder_entries` read lands, which can take a while because the restored files are re-extracted. So when `step` builds `before` for such a file, it reads `null` / `"none"` / `null` instead of what the restored sidecar actually holds (typically the reject), and pushes that onto `redoable`. For example: reject F, trash the rejects, `Ctrl+Z` (restore), then `Ctrl+Z` again quickly. F's reject is undone correctly, but `Ctrl+Shift+Z` now writes "unflagged" instead of re-rejecting F, and the user's reject is lost. Suggested fix: stop deleting `ratings` / `flags` / `labels` for the moved paths in `runTrash`. They are keyed by path and never iterated, so the entries do no harm while the file is out of `allFiles`, and they are exactly right again once the run is undone. The other option is to re-seed those maps from the run before the restored paths go into `allFiles`. Either way, add a comment saying why the maps are kept.
2. **docs/plans/20260928-undo-trash-rejected/plan.md:283-284**: The `pr-rules` require the implementation PR to include "marking the step done + the Progress entry". Step 3's checkbox is ticked, but `## Progress` has no `(2026-09-29) Step 3 complete` line. Add one, matching the Step 1 and Step 2 entries.
