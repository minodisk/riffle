## Round 1

**Reviewed commit**: `cffb1ea3cbb8a27c7e425940806dc27f36a9f1cd` docs: document the XMP sidecars and mark Phase 6 done

STATUS: NEEDS_FIX

### Findings

1. **README.md:105**: "A sidecar the app created is a ten-line RDF/XML template" is false. `template()` in `crates/core/src/xmp.rs` emits seven lines (xpacket, `x:xmpmeta`, `rdf:RDF`, the empty `rdf:Description`, `/rdf:RDF`, `/x:xmpmeta`, xpacket end). Either say seven or drop the count, which carries no information anyway.
2. **README.md:169-172**: "the row is dirty, so rule 4 writes the sidecar the next time that folder is opened" misattributes the recovery. Rule 4 is the *sidecar-absent* case; the common kill-during-debounce case is a file that already has a sidecar whose `(size, mtime)` is unchanged, which is rule 3 ("nothing is parsed"). What actually writes it is the post-reconciliation `dirty_rows` sweep in `reconcile_sidecars_of` (`crates/app/src/commands.rs:222-226`), which runs whichever rule matched. Reword to "the row stays dirty and the next folder open hands every dirty row to the writer", and, if the six-rule list is meant to describe the whole pass, say that the dirty-row sweep is a separate step after the rules rather than one of them.
3. **README.md:167-169**: "`kill -9` or a crash in those 300 ms loses the sidecar write but **not** the judgement" is stated absolutely, but rule 2 contradicts it in one case: if the sidecar's stat differs from the stored one at the next open (it appeared or was edited externally while the folder was open), the sidecar wins and `dirty` is cleared, so the judgement is dropped. Qualify it ("unless the sidecar changed under us, in which case rule 2 applies").
4. **README.md:163-166**: "A sidecar directory that cannot be written (a locked card, a read-only share) fails the rename" is wrong about where it fails. In `sidecar.rs::write` the read-only-directory case fails at `File::create(&temp)` for `FOO.xmp.riffle-tmp`, before any rename (this is exactly what `a_failed_write_leaves_the_row_dirty` exercises). Say "fails the write" and leave the rename out of that sentence.
5. **README.md:161-163**: "renamed over `FOO.xmp`, which is atomic on APFS and NTFS". Nothing in this repository has been run on Windows, and the NTFS half is an unsupported claim of exactly the kind this review exists to catch. Restrict it to APFS, or mark the NTFS half as reported (`std::fs::rename` → `MoveFileEx` with replace) rather than asserted.
6. **README.md:107-116 and 163-166**: two behaviours of the merged code are missing or overstated. (a) `MAX_SIDECAR_BYTES` (4 MiB, `crates/app/src/commands.rs:146`) makes an oversize sidecar neither parsed nor written, and `reconcile_sidecars_of` deliberately filters such a path out of the dirty rows handed to the writer — so for that file "is retried on the next open of that folder" is not true, and the six rules are not the whole story. (b) "A sidecar that is not parseable XML, or that has no `rdf:Description`, is left alone and reported rather than overwritten": the *report* only happens on the write path (`write_rating` → `Err` → the `sidecar-error` event). On the folder-open read path a parse failure is swallowed silently by `.ok()?` in the `filter_map` at `commands.rs:210-214`, with no event and no log. Scope the "reported" to the write path and add a sentence for the oversize case (or state explicitly that it is undocumented on purpose).

### Findings

1. **README.md:150-154**: "A sidecar past `MAX_SIDECAR_BYTES` (4 MiB) ... is neither parsed nor written" is false as an absolute, and this sentence is new in the fix for Round 1 item 6. The 4 MiB limit exists only in `reconcile_sidecars_of` (`crates/app/src/commands.rs:146,204-224`), which is the folder-open path. A keypress on that file while the folder is open goes `set_rating` -> `writer.set` -> `sidecar::write` (`crates/app/src/sidecar.rs:182-197`), which reads the existing sidecar whatever its size and patches it — exactly the "clobbering unread content" the sentence says is prevented. Scope it to the folder-open pass ("the folder-open pass neither parses it nor hands its dirty row to the writer; a rating set while the folder is open still patches it in place").
2. **CLAUDE.md:8-9**: "`src/xmp.rs` reads, writes and patches XMP sidecars" implies file I/O that `crates/core/src/xmp.rs` does not do — it works on byte slices (`read_rating(&[u8])`, `write_rating(Option<&[u8]>, ...)`) and never touches the filesystem; the I/O is in `crates/app/src/sidecar.rs`. Say "parses and patches the XMP sidecar bytes" to keep the split with `sidecar.rs` (described in the same sentence as the writer) honest.
