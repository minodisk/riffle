# Review: live-folder-refresh-step-2

## Round 1

**Reviewed commit**: `b7fddb0b45636ae60a377ffc106d636ec64dae0a` feat(app): watch the open folder and rescan on change

STATUS: NEEDS_FIX

### Findings

1. **[crates/app/src/watch.rs:97 + crates/app/ui/src/main.ts:1193]**: The
   `folder-changed` payload carries the **canonicalised** directory
   (`scan_folder` does `let dir = canonicalize(&dir); crate::watch::set(&app, &dir);`,
   and `set` stores that string as the event `owner`), but the frontend
   compares it with `openDir`, which is the path as picked / passed in
   (`openDirectory(folder, token)` sets `openDir = folder`; nothing on the
   frontend canonicalises). Whenever the two differ, `payload.dir !== openDir`
   is always true and the live refresh silently never fires — the feature
   degrades to Step 1's focus rescan with no log and no visible symptom. This
   is not hypothetical on Windows, where `std::fs::canonicalize` returns a
   verbatim path (`\\?\C:\photos` vs `C:\photos`), and it also bites on any
   symlinked parent on macOS (`/tmp/...`, a symlinked home or volume mount).
   Suggested fix: keep watching the canonical path but emit the *caller's*
   `dir` — capture the original `dir` in `scan_folder` before the shadowing
   `canonicalize` and pass it to `watch::set` as the payload owner (`set(&app,
   &canonical, &original)`), so the payload is exactly the string the frontend
   holds in `openDir`. (Alternatively make the frontend adopt a
   backend-canonicalised `openDir`, but that touches every other `dir`
   comparison, so the first option is the surgical one.)

## Round 2

**Reviewed commit**: `1c77865bd7969bb38355ffeecf188095164daa03` fix: address local review round 1 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 1 / dismissal accepted 0 / re-raised 0

### Findings

1. **[crates/app/src/watch.rs:78-92 (`set`)]**: The Round 1 fix stores `owner`
   by moving it into the event handler closure, but the "same folder, leave it
   alone" early return compares only `dir` (the canonicalised path). So when
   the same folder is reopened under a *different* caller string that
   canonicalises to the same path (a drop with a trailing slash vs the picker,
   `/tmp/x` vs `/private/tmp/x`, a recent-folders entry recorded before a mount
   changed), `set` returns early and keeps emitting the **previous** owner
   while the frontend's `openDir` holds the new string — `payload.dir !==
   openDir` is then always true and the live refresh silently stops, the same
   failure mode as Round 1. Suggested fix: hold the owner in a shared cell
   (e.g. `Arc<Mutex<String>>` cloned into the handler) and update it in `set`
   before the early return, so the watcher is not dropped/rewatched but the
   payload always matches the current caller string. (Comparing `(dir, owner)`
   in the early return also works, at the cost of a rewatch — and a dropped
   Windows directory handle — in that case.)

## Round 3

**Reviewed commit**: `0e3f32143779ac7e82f151ee60893b50fafca1ea` fix: address local review round 2 findings

STATUS: APPROVED

**Previous feedback**: addressed 1 / dismissal accepted 0 / re-raised 0

The shared `Arc<Mutex<String>>` owner is refreshed before the "same folder"
early return and read only inside the event handler, so the payload always
matches the frontend's `openDir`, and the lock order (`Watch` -> `owner` in
`set`, `owner` alone in the handler, never in the debounce thread) cannot
deadlock. The trigger-only use of events, the `triggers` empty-list and mixed-
path cases, the sidecar/temp path filter, the logged-and-ignored watch failure
and the token-guarded `folder-changed` listener all hold; the three unit tests
drive the debounce through its channel, with no file-system event timing.
