### Findings

1. **[crates/app/ui/src/folders.ts:142-147]**: The plan's Done-when says "A right-click or a plain click on the editing row does not open the folder or open the menu", but only the `<input>` stops `mousedown` / `click` / `contextmenu`. A right-click on the editing row outside the input (the indent, the expander, the count) still reaches the row's `contextmenu` listener and opens the folder menu while the edit is live. The container's `mousedown` handler `preventDefault()`s button 2, so focus stays in the input and the edit is not even ended first. Picking `Rename…` from that menu then runs `startRename` on the same path, which confirms the half-typed name through `finish("confirm")` and starts a fresh edit. A left click on the gutter of the editing row avoids opening the folder only by accident: the blur's re-render detaches the row before its `click`. Fix: have the row's `click` and `contextmenu` listeners return early when `editing?.path === node.path` (the container's `contextmenu` listener already suppresses the native menu).
2. **[crates/app/ui/src/folders.ts:97-101, 224-235]**: Clicking another tree row (or its expander) while an edit is live does confirm the rename, but the click itself is lost. The row's `mousedown` moves focus to the `tabindex` container. The input's `blur` runs `finish("confirm")`, and its synchronous `render()` `replaceChildren`s every row between that `mousedown` and the `click`. The `click` then has no attached target, so the folder the user clicked is not opened or toggled. Explorer and Finder commit and then act on the click, and the plan lists "another tree row" alongside a strip cell as an ordinary click away (a strip cell click works, because the strip is not rebuilt). Fix: on the blur path, end the edit without rebuilding the rows. For example, swap the input for a `.name` span in place (`input.replaceWith(span)`) and clear `editing`, leaving the full `render()` to the Enter / Escape path. The alternative is to defer the blur-path `render()` until after the current pointer sequence.
3. **[docs/plans/20260928-rename-from-tree-and-strip/plan.md:459-461]**: Step 2 is checked off, but `## Progress` has no entry for it (only `- (2026-09-28) Step 1 complete`). ### Findings

1. **[crates/app/ui/src/folders.ts:248-263]**: (repeat of Round 1 item 2) The click on another tree row is still lost. `finishInPlace` runs from the input's `blur`, which fires during the row's `mousedown`. `setTimeout(render, 0)` then runs in the very next task, which is long before the user releases the button (a human press lasts tens to hundreds of milliseconds). So the deferred `render()` still `replaceChildren`s every row between `mousedown` and `click`, and the `click` no longer reaches the row the user pressed. A `setTimeout(0)` delays past the current event dispatch, not past the pointer sequence, so the in-place span swap buys nothing here. The same race also applies to the `renamed()` → `render()` that lands when `rename_folder` resolves, since that IPC round trip can finish while the button is still held. Fix: defer the redraw until the pointer sequence ends. For example, in `finishInPlace` register a one-shot `document` `mouseup` listener (`{ once: true }`) that schedules `setTimeout(render, 0)`, because the `click` is dispatched right after `mouseup`, before that timer. Also make `renamed()` wait the same way while a button is down (for instance by tracking a `pointerDown` flag from the container's `mousedown` and the document's `mouseup`, and rendering from the `mouseup` when a render was requested meanwhile). Keep an immediate render when the blur did not come from a pointer press.
