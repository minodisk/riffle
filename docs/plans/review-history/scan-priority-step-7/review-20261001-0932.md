### Findings

1. **[docs/agents/tauri-app.md:1144]**: "Both passes take their files from one `WorkQueue` whose hot list is the `ScanFocus` handle" does not match the code. `for_each_path` (`crates/core/src/scan.rs`) builds a fresh `Mutex::new(WorkQueue::new(paths))` on every call, so `run_scan` and `run_faces_scan` each get their own `WorkQueue`. The only thing they share is the one `ScanFocus` handle stored in `ScansState.running`, which each queue reads as its hot list. Reword it, e.g. "Each pass builds its own `WorkQueue`; both read their hot list from the one `ScanFocus` handle stored in `ScansState.running`". This file is the agent guide future changes rely on, so a wrong model of the queue here is likely to spread.
2. **[CLAUDE.md:51-53]**: Two problems here. First, "pull their files from one shared queue" makes the same mistake as item 1: the passes share the focus handle, not a queue. Second, "both passes run on worker threads below normal OS priority (the second lowest)" reads as if both passes run at the second-lowest level. In fact the first pass is `BelowNormal` and only the second is `Lowest`. Suggested wording: "both passes run on worker threads below normal OS priority (the second pass lower still) and take the on-screen files first through the shared `ScanFocus` handle".
3. **[docs/performance.md:375]**: "The first pass writes each row as soon as its thumbnail is done" overstates it. `run_scan` buffers the results and commits them in batches of `BATCH` (10, `crates/app/src/index.rs`), and `scan-progress` reports them at most every `PROGRESS_INTERVAL`. This section is meant to be a precise cost and latency account, so say "writes the rows in small batches (10) as their thumbnails finish", or drop the timing claim.

### Fixed

All three items were fixed as suggested (wording in `docs/agents/tauri-app.md`, `CLAUDE.md`, `docs/performance.md`).
