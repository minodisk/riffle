## Round 1

**Reviewed commit**: `8f70cc5b81e3f91e5489b5f6b6ae324bbc5bb3bf` feat(app): collect rejects over folders in the backend for trash_rejected

STATUS: NEEDS_FIX

### Findings

1. **crates/app/src/trash.rs:117-143 (`collect_folder`)**: the flag is decided from the newest sidecar of *either* format (`read_listing(dir, Some(SidecarFormat::Both))` + `newest` over `SidecarFormat::Both.kinds()`). The folder open (`scan_folder` → `read_listing(path, Some(format))` → `reconcile_sidecars`) only looks at the sidecar of the *configured* format. So the two can disagree. Example: the setting is XMP, the RAW also has a `.ARW.dop` left over from an earlier `Both` setting or written by PhotoLab, and that `.dop` is newer than the `.xmp` (PhotoLab rewrites `.dop` files on its own). The folder open trusts the clean row and the strip shows the file as not rejected. The collector sees that the row's stat does not match the `.dop`, reads the stale `.dop`, and trashes the file. That is the "trashing a file un-rejected elsewhere" case that the plan's own trade-off section calls the bad one. It also contradicts the plan's "the same rule the folder open applies in `reconcile_sidecars_of`". Fix: pick the effective sidecar for the flag from the configured `SidecarFormat`'s kinds only (pass the format into `collect`, read from `AppSidecarFormat` in `collect_rejected`). Keep using `Both` only to gather the sidecars that get moved with a reject. Add a test where a newer reject `.dop` sits next to a matching clean XMP row under the XMP setting, and check that it is not collected.
2. **crates/app/ui/src/main.ts:571-573**: `summary.failed` now starts with the collection failures (an unreadable folder, a sidecar that does not parse, an index query error). Every entry is still added to the sticky list as `"<name>: could not move to the Trash: <message>"`. For a sidecar that failed to parse on a file that may not even be a reject, or for a folder that could not be listed, that text is wrong: nothing was tried. `trashedStatus` also counts these entries as "N failed" moves. Fix: tell collection failures apart from move failures in `Summary` (for example a separate `unread: Vec<Failure>` field, or a kind on `Failure`). Word the sticky error for those as "could not be read: …", and keep them out of or separate from the moved-failure count. Adapt `trashedStatus` and its test.
3. **docs/plans/20260928-trash-rejected-from-tree/plan.md:246-248**: the plan's `<pr-rules>` require the implementation PR to add the Progress entry along with the step checkbox. Only the checkbox was flipped; `## Progress` still reads `- (none yet)`. Add a Step 1 entry.

## Round 2

**Reviewed commit**: `1b3786a16f5ed768f5a942fc6e172156703cd01c` fix: address local review round 1 findings

### Findings

1. **crates/app/src/trash.rs:485-509 (`a_stray_dop_newer_than_a_matching_xmp_row_is_ignored_under_the_xmp_setting`)**: the test does not make sure the `.dop` is actually newer than the `.xmp`. The two `sidecar(...)` calls run back to back, and on a filesystem with a coarse mtime (HFS+ has 1 s; ext4/NTFS can also land in the same tick) the two mtimes tie. `sidecar::newest` breaks a tie in favor of the first listed kind (XMP), so the test also passes with the old `Both`-based code. It then does not pin the Round 1 fix it was added for. Fix: after writing the `.dop`, set its mtime explicitly later than the `.xmp`'s (for example `std::fs::File::options().write(true).open(&dop)?.set_modified(xmp_mtime + 10s)`, like `set_mtime` in `sidecar.rs`'s tests). Optionally, also check that the same setup *is* collected under `SidecarFormat::Both`, so the test shows that the format argument is what decides.

### Addressed

1. Added a `set_mtime` helper (mirroring `sidecar.rs`'s tests) and pinned the `.xmp` at an explicit mtime and the `.dop` 10 s later, so the test no longer relies on two back-to-back writes landing in different filesystem ticks. Also added a companion assertion that the same setup *is* collected under `SidecarFormat::Both`, showing the format argument is what decides.
