## Round 1

**Reviewed commit**: `d36b894612854807c6360fad960b15cc662d7d03` feat(core): read the AF point from Nikon and Canon AFInfo2 (Step 5)

STATUS: NEEDS_FIX

### Findings

1. **[crates/core/src/nef.rs:110-111]**: `af_point` builds `Tiff::new(buf, at + NIKON_HEADER_LEN, at + len)` and turns every failure into `None`. `Tiff::new` rejects `end > buf.len()`, so if the MakerNote (whose count also covers the embedded `PreviewIFD` JPEG) runs past the 1 MiB `HEAD_LIMIT` prefix that `reader::read_metadata` / `read_embedded` parse first, the AF point is silently dropped. `nef::parse` still returns `Ok`, so the reader never retries with the whole file. Because `EXTRACTOR_VERSION` caches the row, the miss stays until the next version bump. This breaks the contract in `nef::parse`'s doc comment ("a prefix too short to hold ... is never taken for a file ... with fields silently gone missing"). It also differs from `arw::maker_note_ifd`, which returns an error on "MakerNote out of range" so that the reader falls back to the whole file. Suggested fix: when the `Nikon\0` header matches but `at + len > buf.len()` (or the header bytes themselves lie past `buf`), return an error from `parse` rather than `None`. Keep structural oddities inside a note that is fully in the buffer lenient. Add a `reader.rs` test like `a_nef_whose_sub_ifds_are_past_the_prefix_reads_the_whole_file` with the MakerNote moved past the prefix.

## Round 2

**Reviewed commit**: `7d6bef989470c9a3312f1c12ac7c065e5be00680` fix: error out of a truncated Nikon MakerNote instead of dropping the AF point

STATUS: NEEDS_FIX

**Previous feedback**: addressed 1 / dismissal accepted 0 / re-raised 0

### Findings

1. **[crates/core/src/nef.rs:127]**: `let note = Tiff::new(buf, at + NIKON_HEADER_LEN, end)?;` now propagates every `Tiff::new` failure, including ones from a note that sits entirely inside `buf`. `Tiff::new` fails on `end - base < 8` (a note count of 11..=17), on a byte order that is neither `II` nor `MM`, and on a magic number other than 42. A `Nikon\0\x01...` type-1 note with no inner TIFF header would fail this way. In each of these cases `nef::parse` returns `Err`, and the whole-file retry fails the same way, so the NEF loses its preview, full JPEG and every Exif field, not just the AF point. Before this commit these cases produced `None`. It also goes against the fix's own intent, and against Round 1's suggestion to "keep structural oddities inside a note that is fully in the buffer lenient". Suggested fix: the range check above it already covers truncation, so map this error to `Ok(None)` the same way as the lookups after it (`let Ok(note) = Tiff::new(...) else { return Ok(None) };`). Add a `nef.rs` unit test: a `Nikon\0` note fully in the buffer with a bad inner TIFF header should still parse, with `focus == None` and the JPEGs present.
2. **[docs/agents/raw-metadata-parsing.md:126-130]**: The NEF section still says `nef.rs` "errors on any IFD or SubIFD that runs past the buffer". It does not mention the new rule: a `0x927c` MakerNote whose declared range runs past the buffer is now also an error, so that a truncated prefix triggers the whole-file retry instead of caching a missing AF point. Add that sentence, since the next person touching `af_point` needs the lenient-vs-error split (range = error, contents = `None`).
