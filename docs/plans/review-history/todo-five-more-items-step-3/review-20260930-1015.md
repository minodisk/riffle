### Findings

1. **[crates/app/ui/src/folders.ts:455-486]**: `expandAll` recurses into every listed child and has no guard against a directory cycle. `list_subfolders` follows symlinks (`crates/app/src/folders.rs` `kind` uses the followed metadata, and the `symlinked_dir_and_raw_file_are_counted` test pins that), so a folder containing a symlink or junction to itself or an ancestor (for example `a/loop -> a`) keeps producing new, longer paths (`a/loop`, `a/loop/loop`, ...). Each is a fresh node that gets expanded, listed, rendered and watched. It only stops at the OS limit (ELOOP after about 32 to 40 hops, or the path length limit). With two such links in one folder the number of paths grows exponentially, so the walk effectively never finishes and keeps adding `tree-changed` watches. A manual expand does not have this problem because the user decides every step. Suggested fix: bound the walk. The simplest option is to have the backend report whether each child is a symlink or reparse point (for example an `is_link` field on `FolderNode`) and have `expandAll` list such a child without descending into it. Another option is to have the backend return each child's canonical path so the walk can keep a visited set. A depth cap alone is a weaker fallback. Add a `tree.test.ts` or `folders` test case that covers whatever rule you choose, and mention it in `docs/usage.md`'s Expand All sentence.
