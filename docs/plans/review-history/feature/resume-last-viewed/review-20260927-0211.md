## Round 1

**Reviewed commit**: `686bb78dc3256ddaac6b1f6a611094b890040f42` feat(app): resume a folder at the last viewed photo

STATUS: NEEDS_FIX

### Findings

1. **[crates/app/ui/src/main.ts:2227-2231]**: `resumeTarget` runs in `openDirectory` right after `entries.clear()` / `ratings.clear()` (and `flags` / `labels` still hold the previous folder's values, since they are only cleared a few lines later). So `passes` and `ordered()` judge every file as unrated with no capture time, orientation or focus data. The shown-filter sets (`shownFlags`, `shownStars`, `shownLabels`, `shownOrientations`, `shownCandidates`) carry over between folders within a session, so with a judgment-based filter active the resume target comes out wrong. For example, with a "Picks" filter and a remembered file that is picked, nothing passes at open, so `files` is empty and `index = 0`. When `folder_entries` arrives, `refreshEntries` → `refilter()` anchors on `files[index]`, which is `undefined`, and so moves to the first passing file. Its `show()` then overwrites `folders.last_viewed` with that first file, so the remembered position is lost for good. This breaks the plan's "Done when" item "if it is still in the folder but hidden by the strip filter, the nearest passing neighbor is selected". Even with no judgment filter, the nearest-neighbor fallback is taken in the pre-entries order, not in the capture-time order the strip is re-sorted into moments later. Suggested fix: keep `remembered` as a pending resume anchor for the open (cleared on the next folder open), and resolve it in the first `refreshEntries` for that `folderToken`, passing it to `refilter(anchor)` in place of `files[index]` once ratings and entries are loaded. Also suppress, or make harmless, the `show()` write of a provisional fallback before that happens. Add a test for this interaction (for example, extract the "which anchor does the first entries refresh use" decision into `resume.ts`).

## Round 2

**Reviewed commit**: `5e465307b4f93cd1a3515a1f0bcb381a403046a9` fix: address local review round 1 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 0 / dismissal accepted 0 / re-raised 1

### Findings

1. **[crates/app/ui/src/main.ts:1415-1417, 1060-1066]**: The deferred anchor never takes effect when the first `folder_entries` refresh leaves the file list unchanged, and that is the most common case. `refilter(anchor)` returns early at line 1063 when `ordered().filter(passes)` equals the current `files`, and it does so before it looks at `anchor`. With the default name sort and no judgment filter, the list built in `openDirectory` (name order from `list_arw`) is identical to the list after entries load. So `refilter` returns `false`, `index` stays `0`, `pendingResume` has already been cleared, and the folder opens at the first file, not the remembered one. The same happens under capture sort whenever capture order matches name order, and under any filter that entries do not change. The Round 1 finding asked that the remembered file be resolved once entries load, and this path still does not do that (repeat of Round 1 item 1). The `firstEntriesAnchor` tests only exercise a `??` and cannot catch this. Suggested fix: when a resume target was pending, re-anchor even if the list is unchanged. For example, after `refilter(anchor)` returns `false`, resolve `anchorAfterFilter(ordered(), passes, anchor)`. If that lands on a file other than `files[index]`, set `index` and `selection` and call `show()`. Another option is a `force` parameter on `refilter` that skips the early return. Add a test that covers the unchanged-list case, for example by moving the decision "which index should be current after the first refresh, given the old list, the new list and the pending target" into `resume.ts`.
2. **[crates/app/ui/src/main.ts:1443-1450]**: If the first `folder_entries` of an open rejects, the `.catch` never clears `pendingResume`. Because `show()` skips the write while `pendingResume !== undefined`, nothing browsed in that folder is remembered for the rest of the session, and the next open resumes at the stale file. It stays that way until a later `refreshEntries` succeeds, which may never happen once the scan has finished. Suggested fix: in the `.catch`, when `dir === openDir && token === folderToken`, clear `pendingResume`. Ideally also anchor on the pending target, since `files` is already listed.

## Round 3

**Reviewed commit**: `780c11e17cbce1b512e6624ffd8e7637be0bef97` fix: address local review round 2 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 1 / dismissal accepted 0 / re-raised 1

### Findings

1. **[crates/app/ui/src/main.ts:1107-1113, 1428, 1463]**: The forced `refilter` now moves `index` onto the resume target, but it never shows it. When the remembered file still passes, `anchorAfterFilter` returns the anchor itself, so `files[index] === anchor` holds and `refilter` takes the "current file stayed current" branch. That branch only calls `strip.setCurrent(index)` / `renderMeta()`. It does not call `show()`. `openDirectory` already called `show()` for `files[0]`, so the viewer keeps the first file's preview, metadata, status line and crop, while the strip highlights the remembered file. The next keypress then steps from the remembered file, away from what is on screen. This is the main success path of the feature (the remembered file is listed and passes the filter), so resume still does not visibly work (repeat of Round 2 item 1). The same applies to the `.catch` path at line 1463. That branch assumes `anchor` was already the displayed file, and this is the one caller where it is not. Suggested fix: when a pending resume was resolved, call `show()` whenever the resulting `files[index]` differs from the file that was current before the refresh. For example, capture `const before = files[index]` before `refilter` and, if `hadPendingResume && files[index] !== before`, call `show()` (or have `force` also mean "always `show()`"). Extend a test to cover it, for example a pure helper in `resume.ts` that decides whether the view must be re-shown given the previous current file and the resolved one.
