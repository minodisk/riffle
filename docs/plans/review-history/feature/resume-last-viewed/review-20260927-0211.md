### Findings

1. **[crates/app/ui/src/main.ts:2227-2231]**: `resumeTarget` runs in `openDirectory` right after `entries.clear()` / `ratings.clear()` (and `flags` / `labels` still hold the previous folder's values, since they are only cleared a few lines later). So `passes` and `ordered()` judge every file as unrated with no capture time, orientation or focus data. The shown-filter sets (`shownFlags`, `shownStars`, `shownLabels`, `shownOrientations`, `shownCandidates`) carry over between folders within a session, so with a judgment-based filter active the resume target comes out wrong. For example, with a "Picks" filter and a remembered file that is picked, nothing passes at open, so `files` is empty and `index = 0`. When `folder_entries` arrives, `refreshEntries` → `refilter()` anchors on `files[index]`, which is `undefined`, and so moves to the first passing file. Its `show()` then overwrites `folders.last_viewed` with that first file, so the remembered position is lost for good. This breaks the plan's "Done when" item "if it is still in the folder but hidden by the strip filter, the nearest passing neighbor is selected". Even with no judgment filter, the nearest-neighbor fallback is taken in the pre-entries order, not in the capture-time order the strip is re-sorted into moments later. Suggested fix: keep `remembered` as a pending resume anchor for the open (cleared on the next folder open), and resolve it in the first `refreshEntries` for that `folderToken`, passing it to `refilter(anchor)` in place of `files[index]` once ratings and entries are loaded. Also suppress, or make harmless, the `show()` write of a provisional fallback before that happens. Add a test for this interaction (for example, extract the "which anchor does the first entries refresh use" decision into `resume.ts`).
