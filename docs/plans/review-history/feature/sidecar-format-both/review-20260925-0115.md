## Round 1

**Reviewed commit**: `9283781e72dc9757c757336923d280e56fbb87a3` feat(app): add a Both sidecar format that writes the XMP and the .dop

STATUS: NEEDS_FIX

### Findings

1. **[crates/app/src/sidecar.rs:483-486, docs/usage.md:900-902]**: The claim that a half-finished `Both` write ("a failure (or a crash) between them") gets fixed because "the retry or the next folder open writes both again" is wrong for the next-open case. `write` renames the XMP first. If the `.dop` then fails (the retries run out, e.g. a read-only or locked `.dop`) or the app crashes, `mark_written` never runs. The row stays dirty, but its stored `xmp_size`/`xmp_mtime_ns` is still the old stat. On the next open, `reconcile_sidecars_of` computes `newest` and gets the freshly written XMP, whose stat differs from the stored one, so `Index::reconcile_sidecars` queues it for parsing with `dirty = true`. `store_sidecar_ratings` (`WHERE dirty = ?8`) then treats Riffle's own XMP as an external edit, stores it and clears `dirty`. `dirty_rows` returns nothing, and the `.dop` stays stale for good, without any warning. The plan's risk note (plan.md:157-160) makes the same wrong assumption. There are two ways to fix it. (a) Make the claim true: on a partial `Both` failure, record the stat of the sidecar that was written while leaving the row dirty (e.g. a `mark_written` variant that updates only `xmp_size`/`xmp_mtime_ns`). The next open then sees an unchanged stat and replays the dirty row into both files. This is the right fix for the retry-exhaustion case; a crash between the two renames would still leak. (b) At minimum, correct the doc comment and the `docs/usage.md` sentence ("if one write fails, the judgment is retried into both") so they only promise the in-session retry. Either way, add a test: the `.dop` write fails, the retries are exhausted or the writer drains, then run `reconcile_listed` under `Both` and assert the outcome you chose.

The common way to hit a `.dop` write failure is PhotoLab holding the file, which means the user is likely to alt-tab while the retries run. Each attempt has already renamed a fresh XMP into place, and the row still has the old stat. So the focus rescan's `reconcile_sidecars` queues that XMP with `dirty = true`, and `store_sidecar_ratings` stores it and clears `dirty`. When the retries later run out, `mark_partial_write`'s `dirty = 1` guard makes it a no-op, and the `.dop` stays stale for good without any warning. That is the same outcome Round 1 reported. The doc comment on `write` (lines 525-532), `docs/usage.md` ("once the retries are exhausted, the sidecar that did get written is remembered") and the plan's risk note all describe only the exhausted case. Fix: in `flush`, call `mark_partial_write` whenever `e.partial` is `Some`, including before requeueing on the `Some(delay)` branch, not only on the `None` branch. A rescan during the backoff then sees an unchanged stat and keeps the row dirty, and the pending retry (or the re-handed dirty row) still writes the `.dop`. Update the doc comment, `docs/usage.md` and plan.md to match. Extend the test so that it runs `reconcile_sidecars` between a failed attempt and the final one (e.g. drive `flush` with `Some(now)` so the entry is requeued), and assert that the row is still dirty.
