### Findings

1. **crates/app/ui/src/settings.ts:194 (`selectTab`)**: If a Shortcuts row is capturing and the user clicks another tab, `capturing` stays set while the Shortcuts panel is hidden. The next key the user presses (for example ArrowLeft/ArrowRight on the now-focused tab, or any key typed in the Culling tab) reaches the `window` keydown listener and is silently added as a binding to an action they can no longer see. The arrow key also switches tabs at the same time. The plan says focus is never on a tab while capturing, but a click breaks that assumption. Suggested fix: in `selectTab`, cancel any active capture (`if (capturing !== null) { capturing = null; renderShortcuts(); }`), or have the tablist handlers return early while capturing.
2. **docs/plans/20260920-settings-tabs/plan.md:123**: Step 1 is marked `[x]`, but `## Progress` still says `(none yet)`. The plan's pr-rules require the implementation PR to include the Progress entry. Add a Step 1 entry.
