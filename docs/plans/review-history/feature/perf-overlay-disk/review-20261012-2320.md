## Round 1

**Reviewed commit**: `e46a0d333be6e94d56385fe010d1c1a9f22cc167` feat(app): show disk read and disk busy series in the performance overlay

### Findings

1. **[crates/app/src/perf.rs:162]**: `\PhysicalDisk(_Total)\% Idle Time` is the *average* idle time across all physical disks, so on a machine with a system SSD and a separate photo disk (the common layout, e.g. RAW folders on `D:`), a saturated photo disk next to an idle `C:` reads as about 50 % busy. That is the exact scenario this overlay is meant to diagnose (a preview waiting behind a scan that reads RAW files). It also disagrees with the Linux path, which reports the *busiest* disk (`fold(0.0, f32::max)`), and with the module doc and `usage.md` ("how busy the system's disks are"), which do not say the Windows value is an average. Suggested fix: add `\PhysicalDisk(*)\% Idle Time` and read it with `PdhGetFormattedCounterArrayW`, skipping the `_Total` instance and reporting `100 - min(idle)`, which matches Linux's "busiest disk" meaning. If you keep `_Total`, at least say in the module doc and in `usage.md` / `usage.ja.md` that on Windows the line is the average over disks, and note in the plan's trade-offs that it differs from Linux.
2. **[crates/app/ui/src/main.ts:1550-1552]**: The `shown` filter is meant to hide only a series that never has a reading (the comment says "the system disk on macOS"). But while `samples` is empty, which is the first ~1 s after `d` because the first reading is dropped, it also hides `Riffle CPU`, `System CPU` and `Riffle disk`. So the legend opens with just `100%  60 s` and `Latency`, and the other entries pop in with the first sample. Before this change the CPU entries were always in the legend. `learnings.md` describes the delay as affecting only `System disk`, so the code does more than intended. Suggested fix: filter only on samples that exist, e.g. `samples.length === 0 ? PERF_LINES.filter((line) => line.label !== "System disk") : PERF_LINES.filter(...)`. A cleaner option is a `nullable` flag on `PerfLine` with the filter `!line.nullable || samples.some(...)`, so the always-present series are always in the legend.
3. **[docs/plans/20261012-perf-overlay-disk/plan.md:136-138]**: Step 1 is ticked `[x]`, but `## Progress` still says `(none yet)`. The plan's `<pr-rules>` require "the plan.md update (marking the step done + the Progress entry)" in the implementation PR. Add a Progress entry for Step 1. Since the step was ticked on the automated criteria only, the entry should also say that the Windows hand check (the last Done-when item) is still pending, as recorded in `learnings.md`.
