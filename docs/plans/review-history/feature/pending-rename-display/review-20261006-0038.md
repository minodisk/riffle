### Findings

1. **[crates/app/ui/src/main.ts:353 (`cancelPendingRename`), crates/app/ui/src/folders.ts:375 / crates/app/ui/src/strip.ts:753]**: The views' `pending` outlives the `IdleGate` hold. Once `drain()` runs the rename, the slot is empty, but `pending` is only cleared when the `rename_file` / `rename_folder` invoke settles (`clearPending` in the `.then` / error handlers). During that in-flight window, a re-edit of the still-pending cell that confirms the real name gets `editOutcome(...) === "cancel"` and calls `cancelPending()` → `idle.discard()`, which blindly drops whatever is held at that moment. Concretely: a folder rename drains and is in flight (its row still pending), a strip rename is confirmed and held under the next scan, and then the user re-edits the folder row back to its old name. The **strip's** held rename gets canceled (its cell reverts, with `Rename… was canceled`), while the folder rename the user meant to cancel goes ahead anyway. Even without a second hold, the cancel is a silent no-op, and the cell still carries the "Renames when the scan finishes" clock although the rename is already running. Fix: have the cancel name its target, e.g. track the held rename's path in `main.ts` (set in `holdRename` when `held`, cleared in its cancel and at the start of `run`) and make `cancelPendingRename(path)` call `idle.discard()` only when that path matches. Alternatively, treat a pending row/cell whose rename is already in flight as not re-editable. A unit test on whatever pure helper decides this would pin it down.

### Fixed
