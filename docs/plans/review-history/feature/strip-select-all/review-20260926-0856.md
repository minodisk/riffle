### Findings

1. **[crates/app/src/main.rs:289-295, crates/app/ui/src/main.ts:2065-2076]**: Removing the predefined `Select All` means that on macOS, text-field Select All now depends on the custom item's accelerator being `Cmd+A`. In WKWebView, `Cmd+A` in an `<input>` only works through an Edit-menu key equivalent. That is the well-known "Cmd+C/V/A do nothing without an Edit menu" behavior in Tauri apps. Cut, Copy and Paste keep their predefined items, so they are unaffected. If the user rebinds `selectAll` away from `meta+a` (now allowed, since `meta+a` left `MACOS_MENU`), pressing `Cmd+A` in the settings modal's label-name inputs selects nothing. The new key does run the `.select()` fallback, but only through the menu. So the plan's done criterion "Inside a text input of the settings modal, `Cmd/Ctrl+A` still selects the input's text on every platform" only holds for the default binding. Windows and Linux are unaffected, because the engine handles `Ctrl+A` in inputs natively. There are two ways to fix this:
   - Keep native behavior for text inputs no matter what the binding is. For example, in `settings.ts` `keydown`, when the key is `meta+a` (macOS only), the target is a text `<input>`/`<textarea>`, and the modal is not capturing, call `.select()` and `preventDefault()`.
   - Or accept the limitation explicitly. Record it under the plan's "Trade-offs and risks" and in `learnings.md`, and narrow the done-criterion wording to the default binding.
