## Round 1

**Reviewed commit**: `3a2a58fc48cb8fa33bb1962715541b3a5a1a6fa9` feat(app): open a folder by drag-and-drop

STATUS: NEEDS_FIX

### Findings

1. **crates/app/src/commands.rs:99-110**: The doc comment claims `None` covers
   "a file at a filesystem root", but it does not. `Path::new("/a.arw").parent()`
   is `Some("/")` — `parent()` only yields `None` for `/` itself (which `is_dir()`
   already catches) — so a file at the root resolves to `/` and the app would
   happily try to open the whole filesystem root. The `None` arm in practice only
   fires for paths that are neither a directory nor a regular file (gone,
   broken symlink, socket/fifo). Either correct the comment to say that, or, if
   opening `/` really should be refused, implement that refusal explicitly.
   Relatedly, `dropped_directory_is_taken_as_is_and_a_file_by_its_parent`
   (crates/app/src/commands.rs:452-464) only pins directory / file / missing; it
   does not pin any of the behaviour the comment asserts, so the wrong claim went
   unnoticed. Add a case for the boundary the comment describes.

2. **crates/app/ui/src/main.ts:370-378**: Two drops in quick succession are
   ordered by the *response* of `dropped_folder`, not by the drop itself.
   `newFolderToken()` is only called after the invoke resolves, so if drop A
   (folder X) and drop B (folder Y) land in that order but A's `stat` answers
   last, A mints the higher token and X wins — the user's later drop is
   silently overwritten. The deliberate asymmetry (minting late so an ignored
   drop cannot cancel an open picker dialog) is sound, but it needs a second
   guard to keep drops ordered among themselves: capture a monotonically
   increasing drop counter at the moment the `drag-drop` handler runs and return
   early after the invoke resolves if it has been superseded, then mint the
   folder token.

3. **crates/app/src/commands.rs:113-122**: `.ok().flatten()` folds a
   `JoinError` (the `spawn_blocking` task panicked) into the same `None` the
   frontend renders as "Drop a single folder or ARW file." A genuine internal
   failure would be reported to the user as a bad drop. `dropped_dir` cannot
   realistically panic today, but the conflation is free to avoid — e.g. return
   `Result<Option<String>, String>` and let the handler's existing `.catch`
   surface the error.
