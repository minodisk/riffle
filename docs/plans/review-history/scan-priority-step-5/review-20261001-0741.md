### Findings

1. **[crates/app/src/commands.rs:1489 / docs/plans/20260930-scan-priority/learnings.md:820-823]**: `set_scan_focus` is a synchronous command, so it runs on the main thread and blocks on `Scans` with a plain `index::lock`. The learnings entry says the only long holder of that lock is `spawn_eviction`'s `VACUUM`, but that is not true. `clear_index` (`index.clear()`: the drain, the `VACUUM` and the WAL checkpoint), `trash_rejected_run`, `trash_rejected_undo` and `trash_rejected_redo` all hold `Scans` for their whole run. Those runs move files to or from the OS Trash, which can take seconds for a large folder on the Windows Recycle Bin. All of these run only while no scan is running, so today the main thread is safe only because of a frontend rule that Step 6 has not written yet: "send only while scanning". A debounced call that fires just after `faces-done`, right as a held Move Rejected to Trash starts through `idle.ts`, would freeze the whole UI until the move ends. The focus is only a hint, so the fix is cheap. Take the lock with `try_lock` in `set_scan_focus` and drop the call if the lock is busy (a busy `Scans` means no scan is taking the focus anyway). Treat a poisoned lock the way `index::lock` does. The alternative is to make the command `async`, which moves it off the main thread. Either way, correct the learnings entry so it names every command that holds `Scans` for a long time and says which of the two fixes was chosen.

### Fixed

1. `set_scan_focus` now uses `try_lock` (drops the call when busy, recovers a poisoned lock); the learnings entry names every long holder of `Scans` and the chosen fix.
