## Round 1

**Reviewed commit**: `acd56b3bbe1980d5d839a674b8ceaa7c1255bc9e` feat(core): read, write and patch XMP sidecar ratings

STATUS: NEEDS_FIX

### Findings

1. **crates/core/src/xmp.rs:113-170 (`locate`)**: only the *first* `rdf:Description` is considered, but the plan's contract is "the `xmp:Rating` of the first `rdf:Description` **that has one**". Sidecars that split properties across sibling `rdf:Description` elements (what exiftool writes, and what Adobe tools emit when namespaces are grouped) are mishandled in both directions. Verified with a fixture of two siblings, the first carrying only `tiff:Make` and the second `xmp:Rating="4"`: `read_rating` returns `Ok(None)` (an existing rating is invisible to the app, so reconciliation would treat a rated file as unrated), and `write_rating(_, Some(2))` inserts a second attribute into the *first* Description, producing a document with two conflicting `xmp:Rating` values (`2` and `4`) whose resolution is reader-dependent. Fix: in `locate`, keep scanning subsequent `rdf:Description` elements for a `Rating` (attribute or element form) and only fall back to the insert candidate at EOF — i.e. do not return the pending `Location::Insert` on the first `rdf:Description` `End` event, and do not skip attribute inspection once `insert` is `Some`. Add a two-Description fixture to the tests.

2. **crates/core/src/xmp.rs:154-166**: an empty element-form property, `<xmp:Rating></xmp:Rating>`, produces no `Text` event, so `in_rating` is cleared by the `End` event and the pending `Location::Insert` is returned instead. Verified: `write_rating` then emits `<rdf:Description rdf:about="" xmp:Rating="2"><xmp:Rating></xmp:Rating></rdf:Description>` — again two `Rating` properties on one Description. Fix: on the `End` event of the `Rating` element while `in_rating` is still set, splice at the empty range between the start and end tags (which the tracked `pos` already gives) rather than falling through to the insert candidate.
