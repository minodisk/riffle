## Round 1

**Reviewed commit**: `f95ae8107002dcb775226a9b93155411fe7db931` feat(app): add the rename_folder backend command

STATUS: NEEDS_FIX

### Findings

1. **crates/app/src/rename.rs:91-92**: `watch::release_under` runs before `std::fs::rename`, but when the rename fails the watcher is never restored, so the doc comment's "A failed rename changes nothing" does not hold. The plan names the expected failure itself: on Windows another program (PhotoLab, Explorer's preview pane) holds a handle. In that case the open folder (the usual rename target) is left unwatched. Step 2 does not reopen on an error (it only calls `setStatus` and shows the old name again), and the window keeps focus while the user types the name, so the watch stays gone until the next focus rescan or folder switch. Suggested fix: if the rename fails, put the watch back. For example, have `release_under` (or `release`) return the released `(dir, owner)` instead of a `bool`, and call `watch::set(&app, &dir, &owner)` with it before returning the rename error. Add a unit test for `release`'s return value.
2. **crates/app/src/rename.rs:98-107**: If the disk rename succeeds but `rename_dir` fails, the command returns `Err`. The caller then cannot tell this case apart from a rename that never happened. Under Step 2's plan, every backend error puts the old name back on the row and leaves the open folder alone, so the tree would show a folder that no longer exists and the strip would stay on a vanished path. This mismatch between disk and UI is exactly what "disk first, the file system is the source of truth" is meant to avoid. Suggested fix: return `Ok` in this case and carry the warning inside it, e.g. `Renamed { path, warning: Option<String> }`, so the frontend still rebases and reopens and shows the warning in the status line. Update the plan's Step 1 / Step 2 text and the doc comment to match.
