## Round 1

**Reviewed commit**: `3c84fafe822df9da35c1f2d9176f10a8d45c6659` feat(app): follow a folder rename in the trash runs and their undo entries

STATUS: NEEDS_FIX

### Findings

1. **crates/app/src/commands.rs:2268 (`restore_run`, non-macOS)**: on Windows the undo of a run whose folder was renamed never reaches `relocate`, because `::trash::os_limited::restore_all` fails when the original folder no longer exists. The plan and `learnings.md` assume the Recycle Bin recreates the old folder, but trash 5.2.9's Windows `restore_all` builds the destination with `SHCreateItemFromParsingName(item.original_parent)`, and that call fails for a path that does not exist. Only the freedesktop backend runs `create_dir_all(original_parent)`. I checked this on this machine with a probe against `trash = "=5.2.9"`: I trashed `shoot\probe-a.ARW`, renamed `shoot` to `day1`, and called `restore_all`. It returned `Err(Os { code: 0x80070002, "file not found" })`, left the file in the Recycle Bin, and created no folder. So on Windows, the platform this step targets first, every file of a renamed run fails with that OS error, which misses the step's "Done when". Fix: in the non-macOS mover, when `trashed.restore_to` is `Some`, create the missing ancestors of `trashed.path.parent()` before `restore_all`, and keep a list of exactly the folders created. Then have `relocate` remove only those folders, deepest first, each only while it is empty (see item 2). Also correct the claim in `learnings.md` and the new doc comment ("The Trash puts a file back at its original path…") so they no longer say the Windows Recycle Bin recreates the folder. The pending manual check would have caught this, so run it (or a `#[cfg(windows)] #[ignore]` test around a real `restore_all`) before ticking the step.
2. **crates/app/src/trash.rs:686-691 (`relocate`)**: the upward `remove_dir` loop removes every empty ancestor of `from` up to the first non-empty one. It does not check whether the Trash restore created that folder or whether it existed before. Example: after renaming `shoot` to `day1`, the user creates a new empty `shoot` (or a later tree rename gives some other empty folder the old name, or an empty `shoot\sub` exists). Undo then restores into it, and `relocate` deletes the user's folder. The walk does stop at the renamed folder's parent (it holds the renamed folder), and `remove_dir` on a volume root fails, so it cannot climb further. The real problem is that it can delete a pre-existing empty folder. Fix: pass `relocate` the list of folders the restore created (item 1's pre-created list on Windows; on Linux, the ancestors of `from` that were missing before `restore_all`, captured the same way), and remove only those, instead of walking up the whole path. Add a test that a pre-existing empty old-name folder survives `relocate`.
