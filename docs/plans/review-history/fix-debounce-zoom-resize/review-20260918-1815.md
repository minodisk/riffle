# Review: fix/debounce-zoom-resize

## Round 1

**Reviewed commit**: `be4ac5d82414803a228a03290355996ab397d1a9` fix(app): debounce the 1:1 crop request while the window resizes

STATUS: NEEDS_FIX

### Findings

1. **crates/app/ui/src/main.ts:618-622**: `zoomKeypressAt` is set on every `Space`-on transition, but the request it is meant to time is only issued when `crop === null || crop.cropSeq !== seq || cropViewportStale()`. When the held crop is already fresh, no request follows, so `zoomKeypressAt` stays set and is consumed by whatever request comes next — a page turn's `show()` or a debounced resize — which logs a `keypressToPixels` measured from a `Space` pressed arbitrarily long ago. That is the same misattribution this commit set out to remove. Set `zoomKeypressAt` only on the path that actually calls `requestCrop()` (move it inside the `if`), or clear it to `null` in the else branch.

2. **crates/app/ui/src/main.ts:511-520**: `requestCrop()` returns early on `cropInFlight || files.length === 0` before reading and clearing `zoomKeypressAt`, so a `Space` pressed while another crop is in flight leaves the timestamp pending for a later, unrelated request (same class as finding 1, lower severity). Clearing it as part of the early return, or only arming it when a request is actually started, closes both.

3. **crates/app/ui/src/main.ts:169-172**: the debounce callback gates on `cropViewportStale()`, which returns `false` when `crop === null`, so a resize is now silently dropped whenever no crop is held. The reachable case is after a failed `focus_crop` (the `.catch` leaves `crop === null` and `cropInFlight === false`): before this change the resize handler re-fired the request and could recover; now nothing does until the user toggles zoom off/on or pages. Suggest gating as "not zoomed or stale `seq` → drop; `crop === null` or stale viewport → request", e.g. `if (!zoomed || current !== seq) return; if (crop !== null && !cropViewportStale()) return; requestCrop();`. `requestCrop()` already no-ops while a request is in flight, and that in-flight request's settle path re-schedules, so this does not reintroduce the storm.
