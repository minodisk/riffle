### Findings

1. **[crates/app/src/diagnostics.rs:10-29]**: The panic hook runs before `catch_unwind` gets the panic. So every panic that is *caught on purpose* now writes an error-level `panic:` line to `Riffle.log`. This covers the mozjpeg panics on non-JPEG bytes that `riffle_core::scan` (`crates/core/src/scan.rs:124`, "a single corrupt file out of thousands must cost that file and nothing else"), `decode.rs:7/37/200` and `sharpness.rs:188` turn into ordinary `Err`s. The hook cannot tell a caught panic from a crash. Without a note, the agent this log is meant for (the plan's whole point is that `panic:` is the prefix to grep) will read a recovered corrupt preview as an app crash. A folder of corrupt files also adds one such line per file during a scan, and none of these lines go through a flood guard (the JS side has one). The plan's wording "a panic on any thread writes one `panic:` line" allows this, so changing the hook is not required. But the behavior should be written down so the later guide step picks it up. Add an entry to `docs/plans/20261007-agent-readable-app-log/learnings.md` saying that a `panic:` line also appears for panics the core catches and converts to `Err` (the mozjpeg decode / thumbnail / sharpness paths). Such a line is a crash only if no matching recovery follows, for example a scan failure entry for that file. Also note that the `docs/agents/` guide added later must say this. As an optional extra, the doc comment on `install_panic_hook` can mention it as well.
