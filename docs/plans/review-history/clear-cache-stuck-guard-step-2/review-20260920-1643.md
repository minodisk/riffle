## Round 1

**Reviewed commit**: `de7a6aa9feb463fc23ba66f049cf4391b7325231` feat(app): publish the scan state and the index clearing start

STATUS: NEEDS_FIX

### Findings

1. **crates/app/src/commands.rs:1004-1012 (`start_scan`)**: the emit of a constant `true` after `drop(state)` can land *after* the scan task's `false`, leaving the settings window stuck showing "scanning" forever — exactly the failure this feature exists to prevent. The task is spawned before `state.running` is stored, so it starts running immediately and its `finish` block only blocks on the `Scans` lock that `start_scan` still holds. As soon as `drop(state)` releases it, the task can take the lock, `finish(scan_id)`, compute `scanning() == false` (the `scan_folder` call that prepared this scan has already returned, so its `Preparing` is gone and `pending` was emptied by the `remove`) and emit `false` — all before `start_scan` reaches its own `publish_scan_state(&app, true)`. An empty or near-empty `todo` (`scan_folder` inserts a `PendingScan` even when `todo.len() == 0`) makes this window easy to hit. Fix by making the two emits ordered rather than racing, e.g. have `start_scan` publish the value recomputed under a freshly taken lock *after* the task can no longer be pending, or, simpler, emit the `true` before the task is spawnable — sequencing matters here, not just "which value"; emitting the value read under the lock at the moment of the store is not sufficient on its own.

## Round 2

**Reviewed commit**: `9bc06eb7d198c8bd2f9d0ffef3611212017a6214` fix: address local review round 1 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 1 / dismissal accepted 0 / re-raised 0

### Findings

1. **crates/app/src/commands.rs:731-741 (`Preparing::drop`) and 814 (`scan_folder`)**: the same ordering hazard Round 1 raised still exists between these two sites, in the opposite direction. `Preparing::drop` computes `scanning()` under the lock, releases it, and only then emits; a `scan_folder` that takes the lock in that window increments `preparing`, releases, and emits its `true` first, after which the stale `false` lands and the settings window shows "not scanning" for the whole of a scan that is actually running (it only resyncs when the window is reopened, since `scan_running` is queried on open only). The harm is milder than Round 1's (the backend `clear_index` guard still refuses with `SCAN_RUNNING`), but it is the same defect class and the fix is the one already adopted: emit under the lock at both sites, so every `scan-state` emit is serialised by the mutex in the order the state changed. `scan_folder`'s constant `true` would then also become the recomputed `state.scanning()`, removing the last unordered emit.
2. **crates/app/src/commands.rs:694-697 (`publish_scan_state`)**: the doc comment states a contract ("Call it with the lock already dropped: emitting runs listeners on the main thread") that the two new call sites deliberately violate by bypassing the helper, and the stated deadlock rationale is left unreconciled with the fact that emitting under the lock is now the code's chosen ordering mechanism. Rewrite the comment to say why holding the lock across `emit` is safe here (no Rust-side `listen` handler takes the `Scans` lock, and `emit` only queues to the webviews) and when the helper may be used; otherwise the next reader has to rediscover the argument. If finding 1 is applied, the helper may no longer be needed at all.
