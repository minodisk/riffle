## Round 1

**Reviewed commit**: `f04a1848bebd7d6ad467d5ac7fbf3b16b6fe14e6` feat(app): keep the folder tree's expanded folders in sync with the disk

STATUS: NEEDS_FIX

### Findings

1. **crates/app/ui/src/folders.ts:240-250 (`syncWatches`)**: Consecutive `set_tree_watches` calls can be applied out of order in the backend, which then keeps a stale set. Each call replaces the whole set. The command is `async` and does its work in `spawn_blocking` (`treewatch.rs:208-214`), so two invokes sent back to back (expand then collapse with the arrow keys or a double click on the expander, or the reveal chain at launch) run on two blocking-pool threads and race for the `TreeWatch` mutex. If `[A]` wins after `[]`, the backend keeps watching a collapsed folder. On Windows that pins its ancestors, which contradicts the new `docs/usage.md` advice to "collapse it first". If the order flips the other way, an expanded folder is silently not followed. The frontend thinks the set is in sync (`watched` already equals the last set it sent), so nothing corrects this until the set changes again. This is the same class of bug as the "unordered emits leave a stale state" entry in `docs/agents/tauri-app.md` (the `scan-state` note). A related problem: `watched` is set before the invoke, so a rejected call is never retried. Suggested fix: serialize the calls on the frontend. Chain each invoke onto the previous one's promise (e.g. `syncing = syncing.then(() => invoke(...))`) so the next set is sent only after the previous one has been applied. On rejection, reset `watched = ""` so the next render sends the set again.

2. **crates/app/ui/src/folders.ts:563-577 (`tree-changed` listener)**: Permanently deleting an expanded folder shows a spurious error. Examples are `rm -rf` on Linux/macOS or Shift+Delete in Explorer, which remove its entries before the folder itself. Those removals are events *inside* the watched folder, so `tree_paths` maps them to the folder's own key and a `tree-changed` for that folder is emitted. The parent's own `tree-changed` arrives in the same debounce window. When the listener runs, the folder is usually still expanded and drawn: its parent's re-list has not landed yet, or has not even been issued. So `list(dir)` is called on a directory that no longer exists, and `reportError` shows an error for an ordinary external delete. The re-list of a watched folder is a background refresh, not something the user asked for, so a failed listing there should not surface as an error: the parent's re-list is what removes the row. Suggested fix: in this listener only, drop the rejection quietly (e.g. `console.warn`), or report it only when the node is still drawn after its parent has been re-listed. Update the plan's "A listing error is reported through `reportError`" wording to match, and add this case (delete an expanded folder permanently) to the manual checks in `learnings.md`.
