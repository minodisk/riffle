### Findings

1. **[crates/app/src/index.rs:359-368]**: The v11 migration rewrites the judgement columns of clean rows but keeps their `xmp_size` / `xmp_mtime_ns`, so `reconcile_sidecars` treats those rows as up to date and never parses the sidecar again. Before this step, the stored values came from the shimmed readers, which lost information. Under XMP, `read_pick` always returned `false`, so a Lightroom `xmpDM:good="True"` was stored as `pick = 0`. Under both formats, `read_rating` returned `-1` for a reject and dropped its stars. After the migration, those clean rows show no pick for a Lightroom-picked file and show a starred reject as `rating = NULL` until the sidecar's stat happens to change. This defeats the purpose of the step for anyone who opened a Lightroom folder on v10, and the plan's manual check (439 picked) would fail on an existing index. Fix: in the same migration batch, invalidate the stat of clean rows, for example `UPDATE ratings SET xmp_size = NULL, xmp_mtime_ns = NULL WHERE dirty = 0;`, or delete them the way `reset_sidecars` does, so that the next open parses the sidecar again with the real readers. Then extend `a_v10_database_turns_its_picks_and_rejects_into_flags_and_keeps_its_files`, or add a commands-level test, to check that a clean v10 row backed by an XMP with `xmpDM:good="True"` comes back as `Flag::Pick` after the migration.
