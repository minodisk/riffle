### Findings

1. **crates/app/src/commands.rs:3822 (`drain`)**: `assert_eq!(*index::lock(errors), Vec::<String>::new())` fails on a transient error that the writer already recovered from. This makes `a_dirty_row_is_written_to_both_sidecars_after_a_switch_to_both` more likely to fail on Windows than before, which works against the point of this step. Here is how it happens. The test queues with `set_now` (deadline `Instant::now()`), so the writer's `recv_timeout(0)` usually fires before the `Flush` message arrives. The first attempt therefore runs on the deadline path (`flush(Some(now))`). If that attempt fails, for example because a sharing violation outlasts `write_kind`'s ~300 ms of rename retries, `on_error` receives `"... (retrying in 1s)"` and the entry is requeued. The `Flush` that follows then rewrites it. If that rewrite succeeds, both sidecars are correct and the row is clean, so the old test passed, but the new one fails on the stale retry message. The two sibling tests use the debounced `set`, so the `Flush` always gets there first and any error they report is final. Only the `set_now` test is exposed, and it is exactly the Windows-flaky test this step is meant to fix. Only fail on errors that were not followed by a retry. A final failure on the drain path reports `e.message` without the suffix, and a `mark_written` / `mark_partial_write` error has no suffix either, so a filter such as `errors.iter().filter(|m| !m.contains(" (retrying in "))` must come out empty. Put the full list (retry messages included) in the assertion message so a transient sharing violation stays visible in the log. Also put the collected errors in the `"the sidecar writer did not drain"` message, so a timeout shows what the writer had reported so far. This departs from the plan's "the collected errors are empty" wording, so update the side-effect bullet in `docs/plans/20260930-todo-five-more-items/learnings.md` (which currently calls the stricter behavior "intended") to record why only final errors fail the test.
