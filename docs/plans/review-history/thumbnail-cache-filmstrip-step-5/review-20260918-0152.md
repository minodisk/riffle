## Round 1

**Reviewed commit**: `c3fb944474103b6946cfe6b131039baaeb64b7b6` feat(app): add a left thumbnail filmstrip to the window

STATUS: NEEDS_FIX

### Findings

1. **crates/app/ui/src/strip.ts:132 (`request`, success path)**: an object URL can be leaked when the same index is requested twice. `render` deletes an index from `requested` the moment its cell is released, even if that index's `invoke` is still in flight. Scroll the cell out and back in (a single flick up-down) and `pickNext` sees the index as un-requested and issues a second `invoke`. Both responses now find a live cell of the current generation: the first assigns `cell.url = URL.createObjectURL(...)`, the second overwrites `cell.url` without revoking the first, and `releaseCell` can only ever revoke the last one. Over a long fast scroll this leaks one full-size thumbnail blob per duplicated request, which is exactly the growth virtualization exists to prevent. Fix either end: keep a separate `inFlightIndices` set that `render` does not clear (so a re-entering cell does not re-ask), or revoke `cell.url` before assigning a new one. The first is better, since it also stops the wasted IPC.

2. **crates/app/ui/src/strip.ts:120-146**: `inFlight` can be decremented twice for one request, permanently breaking the concurrency cap. `.then` does `inFlight -= 1` at the top and *then* may throw (`new DataView(payload, 0, 8)` on a short payload, or the `unknown thumbnail payload kind` throw). That rejection is caught by the attached `.catch`, which decrements `inFlight` a second time. `inFlight` drifts negative and `pump`'s `while (inFlight < MAX_IN_FLIGHT)` loop then admits more than four — and, in the limit, as many concurrent invokes as there are cells. The same catch also runs the `requested.delete` / `missing.add` bookkeeping for a request that actually succeeded. Move the decrement into a `.finally`, or use a `settled` guard so each request adjusts the counter exactly once.

3. **crates/app/ui/src/strip.ts:141-146 and `refresh` (line 201)**: the rejection path treats *every* error as "not yet scanned", and the only thing that ever retries is `refresh`. Two consequences the string-free assumption does not cover. (a) A genuine permanent failure — a vanished path, a SQLite error, or `thumbnail`'s own `no index cache available` — is swallowed into `missing` exactly like a not-yet-scanned file, so after the final `scan-done` the cell stays a silent gray box with no indication anything failed and no further retry (`refresh` fires only from scan events). (b) In the other direction, while a scan is running `refresh` clears `missing` wholesale on every `scan-progress` tick, so a permanently failing visible cell is re-invoked for the whole duration of the scan. The deferred note in `learnings.md` covers (b) as avoidable IPC, which I accept as a scoping call, but (a) is a correctness gap rather than a performance one: at minimum distinguish "no cached thumbnail" from the rest (the error string is available in the `catch` argument, which is currently discarded), so a real failure is recorded once and shown, rather than being indistinguishable from "still scanning".

4. **crates/app/ui/src/strip.ts:8-13 vs crates/app/ui/style.css:39-67**: the geometry is duplicated with no binding, and the comment that is supposed to document it is wrong. `CELL_HEIGHT = 176` in TypeScript is the sole thing positioning cells, while `.cell { height: 168px }` and the `144x96` image box live only in CSS; nothing in either file names the other, so a CSS edit silently misplaces every cell. On top of that the `strip.ts` comment says "a cell is a 144x144 image box" (the CSS box is 144x96) and "a quarter turn is 144x96 upright" (a quarter turn of 144x96 is 96x144 — the CSS comment states this correctly). Make the numbers one source of truth (e.g. drive the cell height from a CSS custom property read once, or set `el.style.height` from `CELL_HEIGHT - GAP` in `createCell`), and fix the comment so it matches what the CSS actually does.

5. **crates/app/ui/src/main.ts:176-189**: `generation` is bumped in every place the file list changes today, but two overlapping `openFolder` calls can still leave the strip showing the wrong folder. `list_arw` is not sequenced, so opening A then B can resolve B first and A second; the last `setFiles` to run wins and it may be A's, while `scanId` tracking then belongs to B. This is the same shape as the `seq` discipline `requestPreview` already applies and which `generation` mirrors — the gap is that nothing guards the `list_arw` resolution itself. A folder-open token checked before `files = found` would close it.

### Findings

1. **crates/app/ui/src/strip.ts:141-160**: the generation guard is applied in `.then` only; `.catch` and `.finally` mutate bookkeeping that now belongs to the *new* folder (partial repeat of Round 1 item 1, through a path the fix does not cover). After `setFiles` has cleared `requested` / `inFlightIndices` / `missing` / `failed` and the new folder has already re-requested the same index, a straggling response from the old folder does: (a) `requested.delete(index)` / `missing.add(index)` / `failed.add(index)` in `.catch` — so index *i* of folder B is marked `failed` (red cell, never requested again) purely because folder A's file *i* errored, and (b) `inFlightIndices.delete(index)` in `.finally` — which clears the *new* request's entry while it is still in flight. With that entry gone, a single scroll-out-and-back-in makes `pickNext` treat *i* as un-requested and issue a second `invoke`; both responses then find the same live cell of the current generation and the second `cell.url = URL.createObjectURL(...)` overwrites the first without revoking it. That is exactly the object-URL leak Round 1 item 1 asked to close, reachable again via the reopen path. Fix: early-return from `.catch` and from the bookkeeping half of `.finally` when `currentGeneration !== generation`, keeping only `inFlight -= 1` unconditional. Revoking `cell.url` before assigning a new one in `.then` is worth adding as a cheap second line of defense.

2. **crates/app/ui/src/main.ts:204-212**: `folderToken` guards the `list_arw` result but not the scan chain that follows it, so two overlapping `openFolder` calls can leave the strip permanently gray. `scan_folder` is invoked without re-checking `token`, and its `.then` assigns `scanId = scan_id` unconditionally. If A reaches the scan chain while still current and B is opened immediately after, A's `scan_folder` can resolve last and overwrite `scanId` with A's id; every `scan-progress` / `scan-done` event for B then fails the `payload.scan_id !== scanId` test, `strip.refresh()` never fires, and the cells `missing` recorded before the scan produced their thumbnails are never re-requested — they stay placeholders for the rest of the session. (The backend makes this worse rather than better: `scan_folder` cancels whichever scan was running, so the late A call also cancels B's scan.) Check `token !== folderToken` before invoking `scan_folder` and again before `scanId = scan_id`.

## Round 3

**Reviewed commit**: `d5983a1634521cb831adc9c14dcafb6d2037a688` fix: address local review round 2 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 2 / dismissal accepted 0 / re-raised 0

### Findings

1. **crates/app/ui/style.css:105-109 (`#canvas`)**: the main image loses its height, because `min-width: 0` does not replace what the removed `width: 100%` was doing. `#canvas` used to sit in the body's *column* flex container, where `flex: 1` governed the height (main axis) and the explicit `width: 100%` governed the width (cross axis). It now sits in `#main`, a *row* container: `flex: 1` governs the width, and the height is the cross axis, which the rule no longer sets. `align-items: stretch` cannot fill the gap, because stretch only applies when the item's cross size computes to `auto`, and `<canvas>`'s `width`/`height` content attributes map to the `width`/`height` CSS properties as presentational hints. As soon as `draw()` runs it sets `canvas.height = Math.round(height * dpr)`, so from the first frame on the canvas has a definite CSS height equal to `clientHeight * dpr`. On a Retina display (`dpr = 2`) that doubles the element's height on the first `draw()` and doubles it again on every `resize`, so the canvas grows past `#main`, is clipped by `overflow: hidden`, and `draw()`'s `scale = Math.min(width / uprightWidth, height / uprightHeight)` is computed from a height that is not the available height — the image is laid out for a viewport that does not exist. (The width is safe only because `flex: 1` wins over the `width` property on the main axis.) Add `height: 100%` to `#canvas` (`#main` has a definite height, so it resolves), mirroring what `width: 100%` did in the old layout.

2. **crates/app/ui/src/strip.ts:126-146 (`request`, success path)**: a cell that scrolled out and back in while its request was in flight ends up loaded but recorded as un-requested, so it is fetched a second time. `render` does `requested.delete(index)` when it evicts the cell; `inFlightIndices` correctly stops a duplicate *while* the request is pending, but when the response lands in the re-created cell the `.then` assigns the image without restoring `requested`, and `.finally` then drops the `inFlightIndices` entry. The index now passes every `pickNext` filter even though its cell already shows the thumbnail, so the next `pump` issues a redundant `invoke` for a blob the cell already has. The Round 2 revoke-before-assign keeps this from leaking an object URL and `request` re-adds `requested`, so it does not loop — but it is one wasted IPC and one wasted decode per cell that is flicked out and back during a fetch, which is precisely the fast-scroll case. Fix: `requested.add(index)` on the success path of `.then` (after the `generation`/cell guard).
