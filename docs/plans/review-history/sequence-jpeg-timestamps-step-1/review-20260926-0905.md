### Findings

1. **[crates/core/src/sequence.rs:503]**: `read_original` propagates `read_subsec_original(&buf)?`, so a file whose `SubSecTimeOriginal` entry is malformed (an offset or count pointing outside the APP1 segment makes `tiff.bytes` fail at line 198/200) is dropped from the assignment and gets no copy, even though its `DateTimeOriginal` is fine. That contradicts the function's own doc ("`None` when the tag is absent, not ASCII, or not all digits") and the learnings note that a bad SubSec "reads as absent (0) rather than failing the file". SubSec is only a tie-break, so it should never fail the file: either use `read_subsec_original(&buf).ok().flatten()` in `read_original`, or have the 0x9291 branch map a failed `tiff.bytes` / `tiff.u32` to `Ok(None)`, and add a test with an out-of-segment SubSec offset.
2. **[crates/core/src/sequence.rs:579-591]**: `clear_output` deletes every `.jpg` / `.jpeg` that `read_dir(out)` lists, and `process_file` only reads the sources afterwards. If `<folder>-sequenced` already exists as a symlink (or a Windows junction) that resolves to the source folder, the run deletes the user's source JPEGs and then fails every file on read, which is data loss and breaks the plan's "the source is never written" guarantee. A cheap guard: after `create_dir_all(out)`, compare `fs::canonicalize(out)` with `fs::canonicalize(dir)` and return an error when they are equal (before deleting anything).
