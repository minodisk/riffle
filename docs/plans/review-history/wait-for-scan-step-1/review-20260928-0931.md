## Round 1

**Reviewed commit**: `bae86365eab7e86d5bb84535809d458c3a5db312` feat(app): hold Move Rejected to Trash and renames until the scan ends

STATUS: NEEDS_FIX

### Findings

1. **[crates/app/ui/src/main.ts:2132]**: With `renameAllowed` now `() => !viewOnly` and the `scanRunning` check gone from the context-menu branch (~2048), the strip's inline file rename can start mid-scan, but `strip.setFiles` begins with `finishRename("cancel")` (`strip.ts:452`). During a scan, `refilter` rebuilds the strip whenever the filtered/sorted list changes: `refreshEntries` on `scan-progress` / `scan-done`, the forced first refresh after an open with a pending resume, and `faces-progress` while the AF eye filter is on. So a name the user is still typing can be dropped with no feedback. Before this change that could not happen, because the edit could not start during a scan. The folder tree does not have this problem (`folders.ts` `render()` keeps the live editor). Fix this in `strip.setFiles`: when the edited path is still in the new list, carry the edit over to its new index instead of canceling it. If the fix is out of scope for this step, at least keep it from silently discarding typed text, and record the gap in `learnings.md`.
2. **[crates/app/ui/src/main.ts:244-250]**: `settleIdle` stores `idle.inFlight` as a single boolean. When two deferred-operation invokes overlap, the first to settle clears the flag while the other is still out, so `resync()` can start `scan_folder` under it, and the backend's second `SCAN_RUNNING` guard then refuses the operation (the race this flag exists to close). Two ways to get an overlap: a strip file rename confirmed while `renameFolder`'s reopen chain is still pending (that chain now covers `rename_folder` plus `openDirectory`), or two quick renames. Count them instead (for example, `inFlight` as a counter that `settleIdle` increments and decrements, with `resync()` checking `> 0`), or document why an overlap is impossible.

## Round 2

**Reviewed commit**: `c74c43f50afca6b8ab81c56df9b0fbba4f8db205` fix: address local review round 1 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 2 / dismissal accepted 0 / re-raised 0

### Findings

1. **[crates/app/ui/src/strip.ts:458-459]**: The resume branch detaches the focused input (`resume.input.remove()`) while `editing` still points at it, and clears `editing` only afterwards. Detaching a focused element can fire `blur` synchronously (Chromium, and so WebView2 on Windows, does this). The input's `blur` handler then runs `finishRename("confirm")` with `document.hasFocus()` true. That confirms the half-typed name through `rename(...)` in the middle of `setFiles`, calls `render()` against the old `cells` / `files`, and marks the state committed. Then the code below reinstates the same `resume` as `editing`, and the user's eventual Enter goes nowhere (`commit` returns null) or renames from a path that has already moved. `finishRename` itself avoids this by setting `editing = null` before `input.replaceWith(...)`. Do the same here: set `editing = null` first, then `resume.input.remove()`, so a blur fired during the move sees no live edit and does nothing. A test that simulates the blur on removal (dispatch `blur` from a removal hook, or assert the order) would pin it.
