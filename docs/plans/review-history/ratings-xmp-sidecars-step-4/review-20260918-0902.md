A sidecar larger than `MAX_SIDECAR_BYTES` is dropped from `parsed`, so its row keeps `dirty = 1` and is handed to `Writer::set_now`, which patches that sidecar with the app's value — the external edit is overwritten unread. The unparseable case is safe only because `xmp::write_rating` refuses invalid XML; an oversize but well-formed sidecar is not. Either skip the writer for paths whose sidecar was rejected as oversize, or — if this is accepted as a deliberate, negligible case — at minimum correct the learnings.md bullet that currently claims such a file "is never overwritten from either side", since that is not true for the oversize branch.

STATUS: NEEDS_FIX

### Findings

1. **crates/app/src/commands.rs:184-215 (`reconcile_sidecars_of`)**: the lock is
   dropped between `reconcile_sidecars` (which decides what to parse) and
   `store_sidecar_ratings` (which writes `rating` and `dirty = 0`), so a
   `set_rating` that lands in that window is silently discarded: the row's
   fresh rating is overwritten with the sidecar's and its `dirty` flag is
   cleared, so the keypress reaches neither the sidecar nor the index. The
   window is not negligible — `scan_folder` is not awaited by the frontend
   (`crates/app/ui/src/main.ts:575-615` renders and returns before it
   resolves), and on the first open of a folder of foreign sidecars the parse
   covers 5000 files. Decision 3 bounds keypress loss to "the process dies
   between the DOM event and the `ratings` insert"; this widens it to the whole
   parse. Suggested fix: carry the per-path `dirty` value observed in
   `reconcile_sidecars` through to `store_sidecar_ratings` and skip (or leave
   dirty) any row that is dirty now but was not dirty in that snapshot — the
   "sidecar wins over a dirty row" rule should only apply to the dirtiness the
   reconciliation actually saw. The keypress path is not wired until Step 5, so
   nothing is losing data today, but the hole is in this code.
