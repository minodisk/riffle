## Round 1

**Reviewed commit**: `6d103ac028fba834c5196ec03d02c166e70a3f89` feat(app): index folders in SQLite and scan them in the background

STATUS: NEEDS_FIX

### Findings

1. **crates/app/ui/src/main.ts:198-217**: The event filter is `payload.dir !== dir`, which only distinguishes *different* folders. Re-opening the **same** folder while its scan is still running makes the cancelled scan indistinguishable from the new one: the old scan's in-flight `scan-progress` (e.g. `scanning 4000 / 5000`) still passes the filter and overwrites the new scan's count, and the old scan's `scan-done` sets `scanning = null` (or `N failed`) while the new scan is still running, so the progress line dies and never comes back. Also note the old scan emits `scan-done` even when it was cancelled before scanning anything, so `total`/`errors` in that event describe a cancelled run. Fix by carrying a monotonic scan id (or the `Arc<AtomicBool>` generation) in the payload and ignoring any event whose id is not the current one; `dir` alone cannot carry this.

2. **crates/app/src/index.rs:138-177 (`reconcile`) and 223-262 (`entries`)**: `reconcile` only deletes rows whose file is *gone*. A row whose `size`/`mtime_ns` no longer match (the file was modified or replaced) is returned as "to scan" but left in the table, and `entries` selects every row of `dir` without any validity check. If the rescan is cancelled (another folder opened) or the app quits mid-scan, the next `folder_entries` serves the **stale** capture time, focus point and thumbnail for a file that has since changed, with no way for the caller to tell. Either delete the invalid rows in the same transaction that deletes the missing ones, or have `entries` take the current stats and filter/flag invalid rows.

3. **crates/app/src/index.rs:86-99 (`Index::open`)**: on a `prepare()` failure the database is discarded with `std::fs::remove_file(path)` while the original `Connection` is *still open* (`index` is only reassigned afterwards) and **the `-wal` and `-shm` sidecars are left behind**. Since `journal_mode=WAL` is set before the version check, a freshly created `index.sqlite` can be opened next to the previous database's WAL. Drop the connection first (`let Self { conn } = index; drop(conn);` or scope it), and remove `index.sqlite-wal` / `index.sqlite-shm` alongside the main file. On Windows the unlink of the still-open file also fails outright, turning "discard the cache" into a hard error.

4. **crates/app/src/main.rs:18-23**: `Index::open` failing propagates out of `setup`, so the whole app refuses to launch. The index is explicitly a cache (the module doc says so) and neither `list_arw` nor `preview` needs it, so an unwritable cache dir should degrade to "no thumbnails" rather than making the app unstartable. Suggestion: log the error and manage `AppIndex` as optional, or let the index commands return the error string.

5. **crates/app/src/index.rs:181 vs 152-158**: `write_batch` keys the row by `file.path.to_string_lossy()` while `reconcile` builds `listed` with `path.to_str()`, which drops non-UTF-8 paths. A file whose name is not valid UTF-8 is therefore never in `listed`, so its (lossy) row is deleted on **every** `reconcile` and the file is rescanned on every open, forever. Pick one representation for the primary key (lossy in both places, or skip non-UTF-8 files consistently and document it).

6. **crates/app/src/index.rs:292-297 (`flush`)**: a failed `write_batch` adds `batch.len()` to `errors` **on top of** the per-file `errors.fetch_add(1, ...)` already done in `on_item` for files that failed extraction, so `summary.errors` can exceed `summary.total` and the frontend can show more failures than files. The underlying rusqlite error is also swallowed entirely — not even an `eprintln!` like the `extract_all` failure path gets. Count the write failure once (files not already counted) and log the message.

7. **docs/plans/20260918-thumbnail-cache-filmstrip/learnings.md:154-160**: "Second open is 34ms, not seconds" is stated as a headline with the caveat only implied. 5000 **symlinks to one file** means a single inode: the 42ms `stat` is one cached inode looked up 5000 times, not 5000 distinct 48MB files' metadata, so the number is a lower bound and not comparable to a real card folder. The harness was also "removed before committing", so nothing is reproducible. Given the Step 2 precedent of having to correct the 30-second claim, state the measurement conditions inline with the number (symlinks to one file, warm page cache, one inode) and either keep the `#[ignore]`d test or record exactly how to re-run it.

8. **crates/app/src/commands.rs:133-171 / crates/app/src/index.rs (the `dir` column)**: the `dir` key is the raw string the frontend passed through from `pick_folder`, never canonicalized. The same folder reached by a different spelling (trailing separator, a symlinked parent, `/tmp` vs `/private/tmp` on macOS) produces a second, disjoint row set and a full rescan, and `reconcile` for one spelling will not see the rows of the other. Canonicalize once in `scan_folder` and use that for `folder_entries` too.

## Round 2

**Reviewed commit**: `223a53b016870f93ec944a18dcf131fa4392dc5b` fix: address local review round 1 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 7 / dismissal accepted 0 / re-raised 1

### Findings

1. **crates/app/ui/src/main.ts:180-188** (repeat of Round 1 item 1): the `scan_id` scheme is right, but `openFolder` only resets `scanning = null` and leaves `scanId` pointing at the **previous** scan until the new `scan_folder` promise resolves. That promise resolves only after the backend has done `list_arw_in` plus a full `reconcile` (a `stat` of every file and a SQLite transaction), which on a 5000-file folder is tens of milliseconds or more. During that window the just-cancelled scan is still draining its in-flight files and emitting `scan-progress`/`scan-done` with the old id — which still equals `scanId`, so they pass the filter and paint `scanning 4000 / 5000` or `N failed` over the newly opened folder. That is exactly the symptom Round 1 described. Set `scanId = null;` alongside `scanning = null;` before invoking `scan_folder`.

2. **crates/app/ui/src/main.ts:181-188 / crates/app/src/commands.rs:185-214**: `scan_folder` spawns the scan thread *before* returning `ScanStarted`, so the new scan's earliest events are emitted before the frontend has assigned `scanId` and are dropped. Progress is repeated every 100ms so it recovers, but a scan that finishes inside that window loses its `scan-done` for good, and with it the `N failed` count. Either hold the emit until the frontend is known to be listening (e.g. start the scan from a second command the frontend calls after it has stored the id) or keep the last `scan-done` per id so a late-assigned `scanId` can still pick it up.

3. **crates/app/src/commands.rs:156-182**: cancelling the previous scan only stops it from *starting* new files; its in-flight results and the final `flush` still write. `scan_folder` does not wait for that thread, so the old scan's last batch can land **after** the new `reconcile` has already deleted the rows it invalidated, re-inserting a row stamped with the pre-change `size`/`mtime_ns`. `entries` has no validity check, so for the rest of the session `folder_entries` serves that stale capture time/focus/thumbnail (the next `reconcile` does clean it up, so it is not persistent corruption). Joining the previous scan's `JoinHandle` before reconciling closes the window and also stops two scans contending on the index mutex.

4. **crates/app/src/commands.rs:271-274 vs 93-96 / 250-263**: `scan_folder` and `folder_entries` canonicalize `dir`, so index rows are keyed by canonical paths, but `list_arw` still lists from the raw picked path and the frontend's `files[]` therefore holds the uncanonicalized spelling. `thumbnail(path)` looks the raw path up as the primary key and will miss whenever the two spellings differ (a symlinked parent, `/tmp` vs `/private/tmp`). Nothing calls `thumbnail` yet, so this is latent, but it will bite Step 5. Canonicalize in `thumbnail` too, or canonicalize `list_arw`'s `dir` so every command agrees on one spelling.

5. **crates/app/src/index.rs:106-114**: `if index.prepare().is_err()` discards the error without logging, then deletes the database and its sidecars. The intended trigger is a schema-version mismatch, but *any* failure (a full disk, a locked file, a transient IO error) silently destroys the cache with no trace — the same swallowed-`rusqlite`-error problem Round 1 item 6 raised for `flush`, which was fixed there but not here. Log the error before discarding, as `main.rs:26` does for the open failure.

## Round 3

**Reviewed commit**: `134a8e91c6f2b0098c1568d1ba04bf3582ebf986` fix: address local review round 2 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 5 / dismissal accepted 0 / re-raised 0

### Findings

1. **crates/app/src/commands.rs:186-214 (`scan_folder`) / 219-228 (`start_scan`)**: the `Pending` map has no supersession or cleanup. `scan_folder` cancels and joins whatever is in `Running`, but it never touches `Pending`, and `start_scan` spawns any id it finds there and then does `*Running = Some(...)` unconditionally. Two consequences. (a) If `start_scan` is never invoked for an id (the `.then` chain in `main.ts:183-189` never runs — a webview reload, a rejected `invoke`), the entry stays in the map for the process lifetime, holding the whole `Vec<FileStat>` of that folder. (b) If a `start_scan(A)` lands after `scan_folder(B)` has already superseded A — the two `scan_folder` futures are independent IPC tasks and B additionally awaits A's join, so their completion order is not guaranteed — then A is spawned with a `todo` computed *before* B's `reconcile`, and B's own `start_scan` immediately overwrites `Running`, so A is left running with no one holding its cancel flag or its handle: never cancelled, never joined, and its writes land after B's reconcile. That is the exact hole Round 2 item 3 closed, reopened through the split that was introduced to fix Round 2 item 2. Both are fixed by making the id generation authoritative: clear `Pending` in `scan_folder` before inserting the new entry (a superseded queue entry is by definition dead), and/or have `start_scan` no-op unless `scan_id` is the latest id handed out. Cancelling the dropped entries' `cancel` flag is not needed since they never started.

## Round 4

**Reviewed commit**: `95d5b70e9c187ac9dd534e8d67f7a729b8d2e6cf` fix: address local review round 3 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 0 / dismissal accepted 0 / re-raised 1

### Findings

1. **crates/app/src/commands.rs:186-212 (`scan_folder`, the `pending.clear()`)** (repeat of Round 3 item 1, residual): `scan_folder` clears `Pending` unconditionally, without checking that its own `scan_id` is still `LATEST_SCAN_ID`. The two `scan_folder` futures are independent IPC tasks, so the superseded one can reach the clear *after* the superseding one has already inserted. Concretely: `scan_folder(A)` mints id 1 (`LATEST=1`) and blocks in `list_arw_in`/`reconcile`; `scan_folder(B)` mints id 2 (`LATEST=2`), finds `Running` empty (A has not spawned yet, since only `start_scan` fills `Running`), so it does not wait for A, completes, and inserts entry 2; then A resumes, `pending.clear()` **deletes B's entry**, and inserts entry 1. `start_scan(2)` then passes the `LATEST` check but finds no pending entry and silently returns `Ok(())` — B's folder is never scanned at all, no `scan-done` is ever emitted, and the frontend has no way to notice. Guard the insert with the same latest-id check, inside the `Pending` lock so the check and the insert are atomic: `if LATEST_SCAN_ID.load(Relaxed) != scan_id { return Ok(ScanStarted { total, scan_id }); }` placed after `let mut pending = index::lock(...)` and before `pending.clear()`.

2. **crates/app/src/commands.rs:219-228 vs 192-196 (`start_scan`'s `LATEST` check and `*Running = Some(...)`)**: the check of `LATEST_SCAN_ID` and the store into `Running` are not atomic with respect to `scan_folder`'s `LATEST_SCAN_ID.store` / `Running.take()`. If `scan_folder(B)` runs its first two lines between `start_scan(A)`'s `LATEST` load and A's `*Running = Some(...)`, B's `take()` sees `None` (A has not stored yet) and therefore neither cancels nor joins A, A then installs its handle, and B's own `start_scan` overwrites `Running` — leaving A running with nobody holding its cancel flag or handle, its writes landing after B's `reconcile`. That is the same ownership hole as Round 3 item 1 (b), narrowed but not closed, because `LATEST_SCAN_ID` alone cannot serialize against `Running`. Make the id hand-off and the `Running` slot share one lock: have `scan_folder` mint the id and `take()` `Running` while holding that lock (releasing it before the `await` on the join), and have `start_scan` acquire the same lock and re-check the latest id inside it before storing its handle. Then B's `take` and A's store are ordered, and whichever loses is refused.

## Round 5

**Reviewed commit**: `719614e7feb2153c1670682fc805cc7cf9355941` fix: address local review round 4 findings

STATUS: APPROVED

**Previous feedback**: addressed 2 / dismissal accepted 0 / re-raised 0

Folding `next_id`/`latest_id`/`running`/`pending` into one `Mutex<ScansState>` closes both races: `scan_folder`'s mint + `latest_id` store + `running.take()` and `start_scan`'s latest-id check + `pending.remove` + spawn + `running` store are each one atomic critical section, so a superseded id can no longer insert into `pending` or install a handle nobody owns. No deadlock: neither critical section awaits or blocks while holding the lock (the previous handle is joined only after the guard is dropped, and the scan thread touches the index mutex, never `Scans`), and the holistic pass over `index.rs`, `main.rs` and `main.ts` found nothing further.
