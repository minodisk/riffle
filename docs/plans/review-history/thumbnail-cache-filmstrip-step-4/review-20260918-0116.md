## Round 1

**Reviewed commit**: `6d103ac028fba834c5196ec03d02c166e70a3f89` feat(app): index folders in SQLite and scan them in the background

STATUS: NEEDS_FIX

### Findings

1. **crates/app/ui/src/main.ts:198-217**: The event filter is `payload.dir !== dir`, which only distinguishes *different* folders. Re-opening the **same** folder while its scan is still running makes the cancelled scan indistinguishable from the new one: the old scan's in-flight `scan-progress` (e.g. `scanning 4000 / 5000`) still passes the filter and overwrites the new scan's count, and the old scan's `scan-done` sets `scanning = null` (or `N failed`) while the new scan is still running, so the progress line dies and never comes back. Also note the old scan emits `scan-done` even when it was cancelled before scanning anything, so `total`/`errors` in that event describe a cancelled run. Fix by carrying a monotonic scan id (or the `Arc<AtomicBool>` generation) in the payload and ignoring any event whose id is not the current one; `dir` alone cannot carry this.

2. **crates/app/src/index.rs:138-177 (`reconcile`) and 223-262 (`entries`)**: `reconcile` only deletes rows whose file is *gone*. A row whose `size`/`mtime_ns` no longer match (the file was modified or replaced) is returned as "to scan" but left in the table, and `entries` selects every row of `dir` without any validity check. If the rescan is cancelled (another folder opened) or the app quits mid-scan, the next `folder_entries` serves the **stale** capture time, focus point and thumbnail for a file that has since changed, with no way for the caller to tell. Either delete the invalid rows in the same transaction that deletes the missing ones, or have `entries` take the current stats and filter/flag invalid rows.

3. **crates/app/src/index.rs:86-99 (`Index::open`)**: on a `prepare()` failure the database is discarded with `std::fs::remove_file(path)` while the original `Connection` is *still open* (`index` is only reassigned afterwards) and **the `-wal` and `-shm` sidecars are left behind**. Since `journal_mode=WAL` is set before the version check, a freshly created `index.sqlite` can be opened next to the previous database's WAL. Drop the connection first (`let Self { conn } = index; drop(conn);` or scope it), and remove `index.sqlite-wal` / `index.sqlite-shm` alongside the main file. On Windows the unlink of the still-open file also fails outright, turning "discard the cache" into a hard error.

4. **crates/app/src/main.rs:18-23**: `Index::open` failing propagates out of `setup`, so the whole app refuses to launch. The index is explicitly a cache (the module doc says so) and neither `list_arw` nor `preview` needs it, so an unwritable cache dir should degrade to "no thumbnails" rather than making the app unstartable. Suggestion: log the error and manage `AppIndex` as optional, or let the index commands return the error string.

5. **crates/app/src/index.rs:181 vs 152-158**: `write_batch` keys the row by `file.path.to_string_lossy()` while `reconcile` builds `listed` with `path.to_str()`, which drops non-UTF-8 paths. A file whose name is not valid UTF-8 is therefore never in `listed`, so its (lossy) row is deleted on **every** `reconcile` and the file is rescanned on every open, forever. Pick one representation for the primary key (lossy in both places, or skip non-UTF-8 files consistently and document it).

6. **crates/app/src/index.rs:292-297 (`flush`)**: a failed `write_batch` adds `batch.len()` to `errors` **on top of** the per-file `errors.fetch_add(1, ...)` already done in `on_item` for files that failed extraction, so `summary.errors` can exceed `summary.total` and the frontend can show more failures than files. The underlying rusqlite error is also swallowed entirely — not even an `eprintln!` like the `extract_all` failure path gets. Count the write failure once (files not already counted) and log the message.

7. **docs/plans/20260918-thumbnail-cache-filmstrip/learnings.md:154-160**: "Second open is 34ms, not seconds" is stated as a headline with the caveat only implied. 5000 **symlinks to one file** means a single inode: the 42ms `stat` is one cached inode looked up 5000 times, not 5000 distinct 48MB files' metadata, so the number is a lower bound and not comparable to a real card folder. The harness was also "removed before committing", so nothing is reproducible. Given the Step 2 precedent of having to correct the 30-second claim, state the measurement conditions inline with the number (symlinks to one file, warm page cache, one inode) and either keep the `#[ignore]`d test or record exactly how to re-run it.

8. **crates/app/src/commands.rs:133-171 / crates/app/src/index.rs (the `dir` column)**: the `dir` key is the raw string the frontend passed through from `pick_folder`, never canonicalized. The same folder reached by a different spelling (trailing separator, a symlinked parent, `/tmp` vs `/private/tmp` on macOS) produces a second, disjoint row set and a full rescan, and `reconcile` for one spelling will not see the rows of the other. Canonicalize once in `scan_folder` and use that for `folder_entries` too.
