## Round 1

**Reviewed commit**: `e9601913d710b9a7984810d3bcfcbc22206a2234` feat(app): select several folders in the tree and trash their rejects together

STATUS: NEEDS_FIX

### Findings

1. **[crates/app/ui/src/folders.ts:209]**: The plain-click path sets `selection = selectOnly(node.path)` before `open(node.path)` and does not render. The line is redundant, because every open that actually happens goes through `reveal()`, which already resets the selection and renders. It is also harmful when the open does not happen: `main.ts`'s `onOpen` returns early while `formatGate` is closed, and `openDirectory` rejects when `list_arw` / `last_viewed` fails (for example, a folder the user cannot read). In both cases the in-memory selection silently collapses to the clicked folder while the tree still draws the old multi-selection. A right-click on a folder that looks selected then hits `menuTargets`' "not in the selection" branch and acts on that one folder instead of the drawn set. The next unrelated render (a `tree-changed` re-list, an expand) also highlights a folder that never opened. Fix: drop the line and let `reveal()` own the reset. If an immediate reset is wanted, call `render()` right after it, but that still leaves the refused-open case drawing a selection that disagrees with `.current`.
2. **[crates/app/ui/src/folders.ts:497]**: The reset at the end of `reveal()` runs after the `rootsLoaded` wait and the whole chain of `list_subfolders` awaits. `stillCurrent()` guards against a second open, but not against the user selecting folders in the meantime. At launch, while the last folder reopens on a slow volume, or during any open whose chain listing takes a while, a Cmd/Ctrl+click or Shift+click selection made in that window is wiped without notice when the chain lands. The only reason for the second reset is to re-spell the open folder the way the tree keys it. Fix: re-spell it only if the selection is still the one the start of `reveal()` set, e.g. `if (selection.selected.size === 1 && selection.selected.has(path)) selection = selectOnly(current);`, or rebase `path` to `current` inside the existing selection.

## Round 2

**Reviewed commit**: `38245089294b41ac8b236d8e8b15e994d815bb3f` fix: address local review round 1 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 2 / dismissal accepted 0 / re-raised 0

### Findings

1. **[crates/app/ui/src/folders.ts:496]**: The new guard `selection.selected.size === 1 && selection.selected.has(path)` never holds when the folder is opened by a route other than a tree click. `reveal()` sets `selection = selectOnly(path)` and immediately calls `render()`, and `render()` runs `pruneSelection` against the drawn rows. On a drop, File > Open, the launch reopen, or any open of a folder whose chain is not yet expanded, `path` is not drawn yet (and on Windows the caller's raw spelling often differs from the tree's node key anyway), so the prune empties the selection before the first `await`. At the end of `reveal()` the guard then fails and the selection stays empty. The open folder is left out of the selection (`aria-selected="false"`, no anchor), which contradicts the function's own comment "Opening a folder, by whatever route, makes it the selection". It also makes modifier clicks behave differently depending on how the folder was opened: after a tree click, Cmd/Ctrl+click on another folder selects both, and Shift+click selects a range from the open folder. After a drop or launch, the same clicks select only the clicked folder. Round 1 item 2 only needed the reset to skip over a selection the user changed during the awaits, not over one the prune emptied. Fix: detect a user change explicitly instead of inferring it from the selection's contents. For example, bump a module-level `selectionEdits` counter wherever a click or `menuTargets` assigns `selection`, capture it at the start of `reveal()`, and at the end run `selection = selectOnly(current)` when the counter is unchanged. Add a test (or at least a manual check) for the drop / launch route.
