### Findings

1. **[crates/app/src/trash.rs:142]**: `Restored::none` is now dead code on macOS. Its only non-test callers were the two `restore_run`s in `commands.rs`; this commit replaced the macOS one with `trash::restore_recorded(run)`, so only the `#[cfg(not(target_os = "macos"))]` `restore_run` (commands.rs:2196) still calls it. `riffle-app` is a binary crate (`mod trash;` in `main.rs`), so `pub` does not stop the lint. `mise run ci` runs `cargo clippy --all-targets -- -D warnings`, which also builds the non-test bin target, so the macOS CI job fails with `associated function `none` is never used`. The Step 2 learnings list which `dead_code` attributes were dropped or kept, but this one got missed because the Windows machine cannot compile the macOS cfg. Fix: add `#[cfg_attr(target_os = "macos", allow(dead_code))]` to `Restored::none`, the same way `trash_key` / `newest_by_path` do, and note it in `learnings.md`.
2. **[crates/app/src/trash.rs:509]**: `restore_recorded` treats "a file exists at the recorded `trashed_at`" as "this run's file is still in the Trash". macOS reuses a Trash name once it is free. Suppose the Trash is emptied after the run and another file with the same name is trashed from elsewhere, for example in Finder; camera names like `DSC00001.ARW` repeat across cards and folders. That file lands at the same `~/.Trash/DSC00001.ARW`, and Undo then renames the unrelated file into this run's folder, along with any same-named sidecar. The plan's "Trash emptied → not in the Trash" case is exactly when this happens, and the Windows / Linux path does not have the problem because it matches by original path. Fix: at trash time, record the trashed item's identity (e.g. `(dev, ino)` from `std::os::unix::fs::MetadataExt` on `trashed_at`, which a rename inside the volume keeps). In `in_trash`, require a match and otherwise report `NOT_IN_TRASH`. Alternatively, if you judge the risk acceptable, record that decision and its reasoning in the plan's Trade-offs.
